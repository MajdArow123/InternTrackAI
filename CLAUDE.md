# CLAUDE.md

Guidance for Claude Code sessions in this repo. Every statement below was checked against the source on 2026-09-15; where something could not be verified from the repo it says so.

## 1. What this is

InternTrackAI is an AI-assisted internship/job application tracker for people running an internship search, replacing the spreadsheet: a pipeline of applications (list, Kanban board, detail drawer) plus GPT-4o-mini tools that fill forms from postings, score resume fit, write cover letters and interview prep, and turn Gmail messages into status suggestions. Portfolio project by Majd Arow, deployed on Railway.

- Live: https://interntrackai.majdarow.com (custom domain, canonical). The original https://interntrackai-production.up.railway.app is deliberately kept alive so old links and bookmarks keep working, so the app is served on **two** hostnames at once and nothing may pin either — every absolute URL comes from `Request.Scheme`/`Request.Host`, pinned by `ForwardedProtoTests.Every_absolute_url_follows_the_host_the_request_arrived_on`. In particular do **not** set `Google:RedirectBaseUrl`: the OAuth state cookie is host-scoped, so forcing a flow started on one host to return to the other loses the cookie and fails the callback.
- Shared demo account behind the landing page's "Try the live demo" button (`POST /Account/DemoLogin`, credentials from `Demo:Email`/`Demo:Password`). `Services/DemoResetService.cs` reseeds it nightly **only when `Demo__AutoReset=true`**; the code/appsettings default is `false`. The Railway value is not visible from the repo.

## 2. Stack and versions

- ASP.NET Core 9 MVC + Razor views (`net9.0`), ASP.NET Identity (scaffolded Razor Pages in `Areas/Identity`), EF Core 9.
- SQLite locally (`Data Source=app.db`); PostgreSQL in production. `Program.cs` switches to Npgsql when the `DATABASE_URL` env var is set (hand-parses the `postgres://` URI; SSL disabled for `*.railway.internal`, required otherwise).

## 6. Services

OpenAI callers are marked **[AI]**. All read `OpenAI:ApiKey` and treat blank or `your-openai-api-key-here` as "not configured". Only `ProfileExtractorService`, `ResumeScoreService`, `FollowUpService`, `ResumeRewriteService` and `OpenAiStatusClassifier` honour `OpenAI:BaseUrl` (stub endpoint for local verification); the rest hardcode `https://api.openai.com`.

- `ConfiguredAccounts.cs` — the only way to read/match `Demo:Email` and `Admin:Email`: trims config values, compares ignoring case and whitespace, resolves users via `FindByEmailAsync` then `FindByNameAsync`. Used by DemoSeeder, DemoResetService, AdminController, AccountController, `AiRateLimiting.IsDemoEmail`/`IsDemoUser`, `DemoAccountGuardFilter` and the Manage page models (`IsDemoUser`, `DemoUnavailableMessage`).
- `AiRateLimiting.cs` — `AiRateLimitOptions`, singleton `AiUsageLimiter` (per-user fixed-window buckets), `NoAiCallForDemoAttribute`, and the `"ai"` policy + 429 handling. Registered via `AddAiRateLimiting` in Program.cs.
- `JobAnalyzerService.cs` **[AI]** — text or URL (fetches page via named client `UrlFetcher`, strips HTML, 8000 chars) → company, role, location, salary, skills, deadline, interview date. `AnalyzeAsync` is `virtual` with a CancellationToken so tests subclass it. Called by AnalyzerController, CaptureController.
- `ResumeMatcherService.cs` **[AI]** — resume text vs job description → score 0–100, tier (`RecommendationFor`: ≥60 APPLY, ≥40 MAYBE, ≥20 CONSIDER SKIPPING, else SKIP), matching/missing skills, strengths, summary. Static `ExtractPdfText` (PdfPig) is the PDF parser, now called only by `ResumeTextService`. Called by `ProfileController.AutoMatch`.
- `ResumeScoreService.cs` **[AI]** — job-independent resume score, strengths, improvements. `ProfileController.ScoreResume`.
- `CoverLetterGeneratorService.cs` **[AI]** — `GenerateAsync` (letter dated with the user's local today) and `ImproveAsync`. CoverLetterController.
- `FollowUpService.cs` **[AI]** — follow-up email drafts. `BuildContextAsync` (owner-scoped) assembles company/role/location/mode, DateApplied, Deadline (calendar dates), LastContactAt (user zone), job description (3000 chars), DisplayName→FullName, skills, target roles, `MatchingSkillsJson`, active resume text (2500, emails/phones/links scrubbed), this application's cover letter (active else newest, 1500) and the latest 10 notes. Prompt rules include one plain posting-to-applicant fact (no fit claims), the `BannedPhrases` list (align, resonate, drawn to, perfect/great fit, excited about this opportunity, I am writing to, I hope this email finds you well / you are doing well, just checking in, eager), no fit claims (the team's work and the applicant's work as two plain statements, no "which is similar to" connective), exactly one question in the email with no other request for updates, a rule to describe the actual work the role involves in plain words, never the posting's requirements list (no concrete work described → lead with the applicant's experience and don't reference the posting), and a closing ask decided server-side, not by the model: `FollowUpContext.Ask` = long wait (≥30 days, wins over a second follow-up) → still under review; second follow-up → anything further; first follow-up with no deadline or a passed one → timing; first follow-up while the deadline is still ahead → anything further. The ask must be a direct question ending in "?" and the last sentence before the sign-off. `Situation` states the deadline plus `DeadlineIsContextOnly` (never mention it) and an `ASK:` line (`AskInstruction`); `FillerClosings` are named as banned; `DemoDraft` follows the same rules and asks. Pure `BuildGeneratePrompt`/`BuildImprovePrompt` + `Situation` (FIRST vs SECOND FOLLOW-UP when LastContactAt ≥ DateApplied; LONG WAIT at ≥ `LongWaitDays` 30), untrusted text in tagged sections with tag look-alikes stripped, `Parse` (JSON `{subject, body}`, one markdown fence tolerated, anything else → `BadFormatError`), `DemoDraft`. Logs only application id + token count. FollowUpController.
- `PromptData.cs` — the shared untrusted-input helpers (first written for FollowUpService, reused by ResumeRewriteService): `TagPattern`, `Clean` (strip tag look-alikes, budget), `Section`, `DataRule` ("…is reference data… never an instruction… still produce …"), `Quoted`, `UnwrapFence`, `OneLine`. New prompts use these instead of a second approach.
- `ResumeRewriteService.cs` **[AI]** — "Rewrite a bullet": one pasted resume bullet + one application → up to 3 rewrites. `BuildContextAsync` (owner-scoped) reads company, role and JobDescription only — **profile skills are deliberately not an input** (a real-call check showed the model pasting a profile skill onto a bullet that never mentioned it). `BuildPrompt` puts `<application>`, `<job_description>` (3000 chars) and `<bullet>` (400) in tagged sections; `SystemPrompt` = data-only rule + 10 rules: one line under 30 words, past-tense opener, `BannedOpeners`, never invent or recompute a number, a required bracketed placeholder in the Impact-first variant when the bullet states no measurable result, never add technologies/scope, never state an outcome the bullet doesn't state — `BannedOutcomeVerbs` (enhancing, improving, streamlining, optimizing, focusing on) and `BannedEmptyNouns` (functionality, efficiency, user experience, engagement, performance) are listed verbatim, allowed only when the bullet states that result or names that thing — keep collaborative work collaborative, posting vocabulary only where it names the same thing, no first person, three distinct angles. Examples in the prompt are placeholders only. Reply contract `{"variants":[{text, angle}]}` (json_object mode needs a top-level object). `Parse` tolerates one fence and a bare array, collapses text to one line, drops blanks/repeats/over 300 chars, then runs four guards: `InventsNumber`, `InventsOutcome` (vague -ing clause naming nothing from the bullet), `InventsEmptyNoun` and `IsNearDuplicate` (> `NearDuplicateOverlap` 0.6 of the longer variant's distinct words — a Concise compression lands at ~50% and survives). **The floor is one variant**: survivors are returned with `Discarded` > 0 so the endpoint can add `DiscardedNote`; only an empty result is `InventedContentError`. The outcome/near-duplicate guards are lenient by design (the bullet's own verb, a placeholder-only clause, or any one bullet word passes `InventsOutcome`). `NormalizeBullet` strips leading glyphs. `DemoVariants` = fixed rewrites of `DemoSampleBullet`. Logs application id, kept and discarded counts, tokens only. ProfileController.RewriteBullet.
- `InterviewPrepService.cs` **[AI]** — 8–10 questions (`InterviewQuestion` records) and `CritiqueAnswerAsync`. InterviewPrepController.
- `SalaryInsightService.cs` **[AI]** — range + note from model knowledge (not live data). SalaryInsightController.
- `ProfileExtractorService.cs` **[AI]** — `IProfileExtractor`: name, skills, target roles from resume text. Used only via ProfileAutoFillService.
- `ResumeTextService.cs` — **the only way to read a resume's text**. Returns `ResumeTextResult(Status, Text)` with `ResumeTextStatus` = Ok / NoResume / FileMissing / Unreadable / NoText (`MinUsefulChars` 50, the floor the AI endpoints each applied before). Serves `ResumeVersion.ExtractedText` when set, otherwise parses the PDF once via `ResumeMatcherService.ExtractPdfText` and writes it back. Never persists an empty string — a parse that finds nothing leaves the column null so it retries instead of poisoning the row — and a failed write-back still returns the text. `StoreAsync` is the upload-time call. Used by ProfileController (ScoreResume, AutoMatch, AnalyzeResume, UploadResume), CoverLetterController, InterviewPrepController, FollowUpService and KeywordCoverageService.
- `ProfileAutoFillService.cs` — `FillFromTextAsync(userId, resumeText)`: calls `IProfileExtractor`, merges add-never-remove (name only if empty). Takes text, not a path — "no resume / unreadable / no text" is decided by `ResumeTextService` before it is called. ProfileController UploadResume/AnalyzeResume. Rate limiting is the caller's job.
- `SkillAliases.cs` — the one alias map (Node.js, PostgreSQL/Postgres, CI/CD/CICD, Kubernetes/K8s, JavaScript/JS, TypeScript/TS, Go/Golang, React, C#, .NET/dotnet, AWS, REST APIs). `Map` (every lower-cased spelling → canonical display), `Canonical`, `Spellings`. `SkillGapService.Aliases` forwards to it; add new spellings here, never in a second copy.
- `KeywordCoverageService.cs` — "Keyword coverage", the ATS-style literal-term check. **No AI**, so no rate limit, no prompt, no demo branch and nothing cached. Pure `Build(jobDescription, resumeText, company, role, location)` → `KeywordCoverage(Available, Reason, Covered, Total, Missing)`; `Extract` pulls the posting's terms (punctuated tech tokens claimed first so `ASP.NET`/`CI/CD` never re-split, then acronyms, then capitalised runs that don't open a sentence, then cue-phrase captures), and `Present`/`NearMiss` do the matching. Terms count once per line; headings, month names, boilerplate and pay lines (`SalaryLine`) are dropped, as is a candidate containing an interior connective (prose, not a name). Noise rules tuned against branded program postings, which are far noisier than a requirements list: the employer's name is stripped from the front of a candidate when a real name remains ("Microsoft Azure" → Azure) and rejected outright when it isn't, `AddBrandNeighbours` grows the employer's words through name joiners so "Manulife/John Hancock" gives up both halves (plain adjacency deliberately does not, or Azure would vanish), `AddParentheticalAliases` treats an acronym and its bracketed expansion as one name in either order (but only when the bracket holds a single token, or "cloud platforms (IBM Cloud, AWS, or Azure)" would eat its own term), `CurrencyCodes` kills "CAD", two-letter tokens need to be in `ShortAcronyms` (so "AD" goes and "AI"/"ML"/"QA" stay), `RoleNouns`/`DegreeNouns` drop job titles and fields of study whether qualified or bare — you cannot add someone else's job title or a degree you don't hold — and because the capitalised run caps at three words, a run followed by a role noun is dropped with it so "Full-Stack Software Engineer" leaves neither half behind. `AddressLine`/`StreetTypes` and `AuthorizationLine`/`Nationalities` drop office addresses and right-to-work lines; "Drive" and "Way" are deliberately not street types ("Google Drive"). Ordering is frequency + 2 under a requirements heading, ties alphabetical. `MaxMissing` 15 caps the list but not the `Total`; `MinTerms` 10 is the "too short" floor. Reasons: `NoDescription`, `NoResume`, `UnreadableResume`, `TooShort`. JobApplicationsController.KeywordCoverage.
- `ProfileTags.cs` — the single definition of "same tag" (trim, collapse whitespace, case-insensitive, first casing wins); JSON helpers. Mirrored client-side by `wwwroot/js/tag-input.js`.
- `ReminderService.cs` — the only place for "needs attention" rules: Overdue (deadline passed, still Saved), DeadlineSoon (≤7 days, not Offer/Rejected), FollowUpDue (Applied, anchor = later of DateApplied/LastContactAt, ≥ `FollowUpAfterDays` 3–30 default 7, not snoozed), UpcomingInterview (≤14 days). Snooze = 3 days. Used by HomeController (Attention card), JobApplicationsController (list filter, board/drawer chips via `ViewBag.AttentionById`, mark contacted/snooze), ProfileController (window bounds). The calendar feed does not use it; `IcsBuilder` emits raw dates.
- `IcsBuilder.cs` — hand-written RFC 5545 (escaping, 75-octet folding, VTIMEZONE from host tz data). CalendarController.
- `UserClock.cs` — `UserClock` (pure UTC↔zone conversion + formatting) and scoped `UserClockProvider` (per-request cached; `ForUserAsync` for the anonymous feed). Injected into every view as `Clocks`.
- `TimeZones.cs` — IANA catalogue/dropdown groups; `Resolve` falls back to `America/Toronto` for unknown ids.
- `ResumeAnalyticsService.cs` — "Resume performance": per resume version, sent (status ≠ Saved), responses (currently Interview or Offer), rate, low confidence under 5; card shows at ≥ 2 resumes. HomeController, ProfileController.
- `SkillGapService.cs` — "Skills you're missing most": aggregates stored `MissingSkillsJson`, no AI. HomeController. Rules in section 12.
- `CsvImportParser.cs` — pure parser for the Export column layout; skips rows without company/role, drops duplicates. `JobApplicationsController.ImportCsv`.
- `UploadStorage.cs` — singleton; root from `UPLOADS_PATH` (default `./uploads`). `photos/{userId}.{ext}` (public at `/uploads/photos`), `resumes/{userId}/{guid}.pdf` (private). `Resolve` rejects rooted/escaping stored paths and tolerates legacy `uploads/` prefixes.
- `UserDataPurger.cs` — deletes all of a user's rows and files; `keepProfile`/`keepActiveDocuments` for the demo reset. Used by `Areas/Identity/Pages/Account/Manage/DeletePersonalData.cshtml.cs` and DemoSeeder.
- `DemoSeeder.cs` — purges the demo user (keeps profile + active resume), ensures two resumes ("Backend focus" active, "General"), and restores every profile field it owns rather than leaving a visitor's edit: `TargetRoles` (Software Engineer / Backend Systems Engineer / Frontend Product Engineer), `Skills`, `DisplayName` "Demo User" (backstop for the display-name guard), `FullName` and `Country`. Seeds 15 applications, notes, 1 cover letter, 3 pending suggestions. **`Skills` must stay consistent with the seeded match data**: every entry appears in some application's `matching` list and none in any `missing` list, so the profile can't contradict the skill gap card. `DemoResetTests` pins that the fields are replaced, not merged. AdminController, DemoResetService.
- `DemoResetService.cs` — hosted service; daily at `Demo:ResetTimeUtc` (default 04:00) only if `Demo:AutoReset` is true and `Demo:Email` is set; logs which at startup.
- `EmailSender.cs` — the email contract: `EmailMessage(Subject, Html, Text?)`, `IAppEmailSender` (extends Identity's `IEmailSender`, which the compiled Identity UI pages resolve directly, with a text part and a cancellation token) and `ConsoleEmailSender`, which logs the message instead of sending it. `ConsoleEmailSender` is the fallback whenever `Resend:ApiKey` is unset — normally local development — not a development-only class.
- `EmailTemplates.cs` — the one place an outgoing email's HTML and plain text are written; a static method per email over a shared `Layout`, deliberately not a templating system. `PasswordReset(resetUrl, lifespan, recipient)` takes the real `DataProtectionTokenProviderOptions.TokenLifespan` so the stated expiry can't drift from the token, and the address the message is going to (what the visitor typed, not the account's canonical email) for the footer's "Sent to … because" line. Nested `<table>` layout at 600px — set by both the `width` attribute (Outlook) and inline `max-width` — with inline styles and literal hex mirroring the `site.css` tokens (mail clients can't read CSS custom properties, and many strip `<style>` blocks), a system font stack, no image, stylesheet, font or tracking pixel, and **never the literal `http://`** — a bare `<!doctype html>`, no `xmlns`, because `ForwardedProtoTests` asserts the body contains no `http://` at all. The brand dot is a 10×10 `<td>` with `bgcolor` inside its own single-cell table (a plain cell stretches to the row height and ovals); it squares off in Outlook's Word engine, which is the whole degradation. A hidden preheader span opens `<body>` so the inbox snippet is the email's purpose.
- `RegistrationRateLimiting.cs` — `RegistrationRateLimitOptions` (`RateLimiting:Registration`: `PerIpPerHour` 5, `WindowMinutes` 60) and the singleton `RegistrationLimiter`. Same fixed-window primitive and the same in-page placement as `PasswordResetLimiter` — the permit is taken in `Register.OnPostAsync` once the form is otherwise valid and before `CreateAsync`, so it bounds attempts, not successes, and a refusal re-renders the form with the reason under a 429 (`PageResult` writes a content type, so the status-code pages middleware doesn't re-execute it as a 404). Keyed by `PasswordResetLimiter.IpKey`, so "one client" means the same thing on both anonymous endpoints. Unlike ForgotPassword there is no oracle to protect: Register already has to say "that address is taken".
- `PasswordResetRateLimiting.cs` — `PasswordResetRateLimitOptions` (`RateLimiting:PasswordReset`: `PerIpPerHour` 5, `PerAddressPerHour` 2, `WindowMinutes` 60) and the singleton `PasswordResetLimiter`. Same built-in fixed-window primitive as `AiUsageLimiter`, but permits are taken **inside the ForgotPassword page**, not through the `"ai"` HTTP policy: that policy answers with a 429 and a toast, and this page must answer a refusal with the identical confirmation or the limit becomes the account oracle. `Allow(ip)` runs before the account lookup so probing costs the prober; `AllowSendTo(email)` runs only when a message is about to go out so probes can't burn a real user's allowance. IPv6 keys collapse to the /64 (a subscriber owns 2^64 addresses); addresses are never stored — the key is a salted SHA-256 under a per-process salt.
- `ResendEmailSender.cs` — `POST {Resend:BaseUrl}/emails` with a bearer key; `to` is always an array, `text`/`reply_to` are omitted when null. Retries **once** on a 5xx, a 429 or a network failure (after `Retry-After` when given, else 1s), never on any other 4xx; both attempts reuse one `Idempotency-Key` so a retry after a lost response can't double-send, and `Budget` caps the pair at 15s. It **never throws** on a send failure and never logs the recipient, the subject's body, the HTML/text or the link: failures log status + Resend's error `name` + the message passed through `Redact`, because Resend echoes the recipient back in validation errors (``Invalid `to` field someone@example.com``).
- `GitHubService.cs` — unauthenticated GitHub REST, up to 6 public non-fork repos for the profile; 10 s timeout, null on any failure.
- `Services/Gmail/`:
  - `GmailOptions.cs` — `GoogleOptions` (`Google:*`), `GmailOptions` (`Gmail:*`: SyncIntervalMinutes 30, MaxMessagesPerSync 50, MaxBodyChars 4000, stub endpoint overrides), `GmailIntegration.IsConfigured`.
  - `GoogleOAuthClient.cs` / `IGoogleOAuthClient.cs` — auth URL (`gmail.readonly`, offline, prompt=consent), code exchange, refresh, revoke.
  - `GmailApiClient.cs` / `IGmailClient.cs` — read-only profile/list/get; maps headers, snippet, first text/plain part.
  - `GmailTokenProtector.cs` — Data Protection encryption of stored tokens.
  - `CompanyDomains.cs` — candidate sender domains from company name, job link, note emails; ignores generic mailboxes.
  - `StatusClassifier.cs` **[AI]** — `IStatusClassifier` / `OpenAiStatusClassifier`; only Interview/Offer/Rejected survive `Parse`.
  - `GmailSyncService.cs` — one user's sync: refresh token, query (`newer_than:30d` first, then `after:LastSyncedAt`), match message → application, classify (one `AiUsageLimiter` permit each), store `StatusSuggestion`. Called by IntegrationsController.Sync and the hosted service.
  - `GmailSyncHostedService.cs` — every `SyncIntervalMinutes`, per-user scope + try/catch; idle when Google keys are absent.
  - `SuggestionService.cs` — owner-scoped pending lists/counts, Accept (applies status + interview time, adds note "Status updated from email: …"), Dismiss. Used by Home, JobApplications, SuggestionsController, `_Layout.cshtml` nav badge.

## 8. Cross-cutting rules

**Ownership.** Every action taking a record id loads it with `Id == id && UserId == currentUser` and returns `NotFound()` (JSON `{success:false,error}` for fetch endpoints) on a miss — never 403, and never a silent no-op. 404 makes "not yours" indistinguishable from "doesn't exist", so ids can't be probed. Bulk endpoints silently ignore foreign ids. Foreign ids in bodies (e.g. `applicationId` on cover letter Save, `ResumeVersionId` on Create/Edit) are rejected or dropped. Every new id-taking endpoint gets a test in `tests/InternTrackAI.Tests/Integration/OwnershipTests.cs` (or the feature's endpoint test file).

**Configured accounts.** Never read `Demo:Email`/`Admin:Email` with `config[...]` or compare them with `string.Equals`/`==`; go through `Services/ConfiguredAccounts.cs`. Railway variables can carry surrounding whitespace, which Identity's lookups don't trim, and a LINQ `u.Email == x` is case-sensitive on both providers. Look users up only through `UserManager` (normalised columns). Callers today: `AiRateLimiting`, `DemoAccountGuardFilter`, the Manage page models, `DemoSeeder`, `DemoResetService`, `AdminController`, `AccountController` and `ForgotPassword`.

**Rate limiting.** Policy `"ai"` (`Services/AiRateLimiting.cs`): one fixed window per user id (IP for anonymous), `RateLimiting:AI:PermitLimit` 20 per `WindowMinutes` 60, `DemoPermitLimit` 10 when the signed-in email equals `Demo:Email`. Shared across every AI endpoint. Rejection: 429 + `Retry-After`; JSON `{success:false, hasResume:true, rateLimited:true, error}` for JSON/XHR callers, otherwise redirect to the local referrer with an error toast. Work outside a request draws from the same `AiUsageLimiter` bucket: each Gmail classification, and resume-upload auto-fill. Every new OpenAI call must be tagged `[EnableRateLimiting(AiRateLimiting.PolicyName)]` or take a permit manually. `[NoAiCallForDemo]` on an "ai" action makes the policy hand the demo account a no-limit partition there; use it only when the action's demo branch returns before any model call (today: FollowUp Generate/Improve and Profile RewriteBullet, pinned by `RateLimitTests.Demo_permit_exemption_is_only_on_the_reviewed_canned_actions`). Resume auto-fill skips its manual permit for the demo account in `ProfileController.AutoFillToastAsync`, and the demo can't connect Gmail, so no other demo path draws a permit without an AI call.

**Anonymous endpoints that mint something.** Registration and password reset are both anonymous and both hand out something scarce (an account, an email), so each carries its own per-client fixed-window bucket taken *inside the page model* — `RegistrationLimiter` and `PasswordResetLimiter`, both keyed by `PasswordResetLimiter.IpKey`. The `"ai"` HTTP policy is the wrong tool for either: its rejection path redirects a form post to the referrer with a toast, which reads as the form losing the visitor's input. `Register` answers a refusal with the form plus the reason under a 429; `ForgotPassword` answers with the identical confirmation it shows on success, because there the refusal must not become the oracle.

**Email.** One seam, `IAppEmailSender` (`Services/EmailSender.cs`), backed by `ResendEmailSender` when `Resend:ApiKey` is set and `ConsoleEmailSender` otherwise; `IEmailSender` is registered onto the same choice because Identity UI's compiled pages resolve it. Bodies belong in `Services/EmailTemplates.cs`, never inline in a page model, and always ship an HTML and a text part. Two rules a new email must not break: **a send failure never changes what the user sees** (senders log and return rather than throw, so a page can't become an account oracle), and **nothing identifying is ever logged** — not the recipient, the body or the link, and provider error text goes through `ResendEmailSender.Redact` first because Resend echoes the recipient back. Anything emailed to `Demo:Email` is refused before a token is minted. **Any anonymous endpoint that can send must be limited or switched off**, and a refusal must be indistinguishable from a send: `ForgotPassword` carries `PasswordResetLimiter`, and `/Account/ResendEmailConfirmation` — which Identity UI maps, anonymous, backed by `IEmailSender`, and which really did turn 12 posts into 12 sends — is 404'd by `Areas/Identity/UnusedIdentityPageFilter.cs`.

**Security headers.** Kestrel's `Server: Kestrel` banner is off (`builder.WebHost.ConfigureKestrel(o => o.AddServerHeader = false)` in Program.cs, pinned by `SecurityHeaderTests.Kestrel_does_not_advertise_itself` — asserted on the option because TestServer is not Kestrel). `Services/SecurityHeaders.cs` is the one place the remaining headers' values are written; `app.UseSecurityHeaders()` sits directly after `UseForwardedHeaders` and **above `UseStaticFiles`**, which short-circuits — register it any lower and CSS, JS and uploaded files go out bare. Every response, static files / `/health` / redirects / the re-executed 404 included, carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: strict-origin-when-cross-origin`. The CSP ships as **`Content-Security-Policy-Report-Only`**, never enforced, because `_Layout.cshtml` (theme pre-paint, toast, shortcuts) and `Views/InterviewPrep/Prep.cshtml` still carry inline scripts — and for the same reason `script-src` is `'self'` with **no `'unsafe-inline'`**: the browser console reporting each remaining inline block is the list to work through before this can be enforced, and granting `'unsafe-inline'` would silence the report without changing the exposure. The policy names the only third-party origin in the app (Google Fonts, `fonts.googleapis.com` + `fonts.gstatic.com`) and `img-src blob:` for the profile photo preview in `profile.js`; `form-action 'self'` is safe for Gmail OAuth because Connect leaves by a 302, not a form post, and jsPDF's `doc.save()` is untouched by any directive. Headers are written in `Response.OnStarting` so they win at flush time regardless of pipeline order. Adding an origin, or enforcing the policy, means changing that one file and `Integration/SecurityHeaderTests.cs`, which pins the values on an MVC page, an Identity page, `/health`, a static file, an authenticated page, a redirect and the 404. There is no `report-uri`/`report-to` endpoint: violations surface in the browser console only.

**Forwarded headers.** Railway terminates TLS and forwards plain HTTP. `UseForwardedHeaders` (For, Proto, Host) must stay the **first** middleware, and `KnownNetworks`/`KnownProxies` stay cleared: the defaults trust loopback only, Railway's proxy connects from a private address, and the headers were silently ignored (Gmail `redirect_uri_mismatch`, http:// reset links). All absolute URLs come from `Request.Scheme`/`Request.Host` (Gmail redirect URI unless `Google:RedirectBaseUrl` is set, password-reset links, bookmarklet code, calendar feed URL) and must come out https in production — guarded by `Integration/ForwardedProtoTests.cs`. `UseHttpsRedirection` runs only in Development (it would loop behind the proxy).

**Resume text.** Never call `ResumeMatcherService.ExtractPdfText` from a controller or a feature service — go
through `ResumeTextService`. It extracts once and stores the result on `ResumeVersion.ExtractedText`, so a user
who triggers a score, a match, a cover letter and a follow-up parses the PDF once, not four times. The stored
text can never go stale: a version's file is immutable (a new upload creates a new row), so switching the active
resume selects a different row rather than invalidating anything. Branch on `ResumeTextResult.Status` rather
than re-implementing the "is there enough text" check; `Text` is populated even for `NoText` so best-effort
callers (cover letter, interview prep) can use `.Text ?? ""` and ignore the status.

**Time in tests.** Integration tests can't pin the clock, so seed dates through `Integration/TestClock.cs`, never
`DateTime.UtcNow.Date`: a registered user has no `TimeZoneId` and therefore gets `America/Toronto`, whose date
disagrees with UTC's for the last four hours of every summer evening. `TestClock.Today` for calendar dates
(Deadline, DateApplied), `TestClock.Instant(localDate, hour)` for the instants (InterviewAt, FollowUpAt,
LastContactAt) — seeding one of those as a bare local value drifts the hour and can cross midnight. Plain
`DateTime.UtcNow` stays correct for instants that are only ever compared with other instants (token expiry,
email dates, note timestamps). Unit tests pin a fixed clock instead and need none of this.
`ReminderServiceTests.Every_rule_and_its_wording_is_identical_morning_and_evening` guards the service side, so a
date test failing only in the evening is a bad seed, not a rule.

**Time.** Store UTC; convert only through `UserClock`. In views: `var clock = await Clocks.GetAsync();`. Calendar dates (Deadline, DateApplied) are never shifted: `clock.Date(...)`. Instants (InterviewAt, FollowUpAt, LastContactAt, note/upload/generation stamps): `clock.LocalDate/LocalDateTime/LocalTime`. Create/Edit forms bind InterviewAt/FollowUpAt with `asp-for`, so the controller converts the entity before render and after post (`UtcToForm`/`FormToUtc` in JobApplicationsController). `UserClock.InputDateTime/InputDate` exist but are currently unused. "Today" for any N-days rule is `clock.Today`. Never `DateTime.Now`, never `.ToString(...)` a DateTime for display in a view (the one existing raw format, `Views/JobApplications/Edit.cshtml` LastContactAt hidden input, is a UTC round-trip, not display).

**Migrations.** `dotnet ef migrations add` scaffolds against SQLite: DateTime columns come out `type: "TEXT"` (on Postgres that becomes a `text` column: inserts coerce, every read throws `InvalidCastException`), `double` as `REAL` (float4 on Postgres), and new tables get only `Sqlite:Autoincrement`, so Postgres inserts fail with 23502. Rule: every migration that adds/alters a DateTime, floating-point or identity column must branch on `migrationBuilder.ActiveProvider == "Npgsql.EntityFrameworkCore.PostgreSQL"` (`timestamp with time zone` / `double precision` vs `TEXT` / `REAL`) and add `.Annotation("Npgsql:ValueGenerationStrategy", NpgsqlValueGenerationStrategy.IdentityByDefaultColumn)` to new identity keys. Templates: `20260913225431_AddGmailConnections.cs`, `20260913230212_AddStatusSuggestions.cs`. Verify with `tests/InternTrackAI.Tests/MigrationColumnTypeTests.cs`, which replays all migrations through the Npgsql SQL generator (no DB): it fails automatically on any non-timestamptz date column, but the identity check only covers tables listed in its `[InlineData]` — add every new table there. Optional real-Postgres check: `Integration/PostgresMigrationTests.cs` with `INTERNTRACK_PG_CONNECTION` set (drops and recreates that database). `PendingModelChangesWarning` is suppressed on Npgsql in Program.cs because the snapshot is SQLite-flavoured.

**Views and JS.** Large views are split into partials (`Views/Home/_*.cshtml`, `Views/JobApplications/_*.cshtml`, `Views/Profile/_*.cshtml`, `Views/CoverLetter/_*.cshtml`). Page behaviour lives in `wwwroot/js/<page>.js`, one IIFE per file, loaded from the view's `Scripts` section; no new globals. Server data reaches JS via `data-*` attributes or JSON islands (`<script type="application/json" id="appsOverTimeData">`, `id="skillGapData"` in `Views/Home/Dashboard.cshtml`). No new inline `<script>` blocks. Existing exceptions, don't copy them: theme pre-paint in `_Layout.cshtml` and `_AuthLayout.cshtml`, toast + theme toggle + keyboard shortcuts in `_Layout.cshtml`, and the inline IIFE still in `Views/InterviewPrep/Prep.cshtml`. Intentional shared globals: `site.js` functions (`showAppToast`, `appConfirm`, `shakeField`, …), `window.TagInput`, `window.reminderAction`, `window.suggestionAction`. Confirm dialogs: add `data-confirm` to a form (global styled confirm in `_Layout`). Toasts from the server: `TempData["Toast"] = "success|message"` (also `info`, `error`).

**Design.** `wwwroot/css/site.css` is the only design system: tokens on `:root`, dark overrides on `html[data-theme="dark"]` (theme stored in `localStorage.theme`). Use tokens for every new colour; no new palettes, no second design system, no inline colour styles. The one exception is `Services/EmailTemplates.cs`: mail clients support neither CSS custom properties nor external stylesheets, so email HTML inlines the literal token values — keep them in step with `site.css`. Some older rules still hold literals (e.g. `.btn-danger { background:#DC2F27 }` for 4.7:1 contrast, dark navbar rgba values, Chart.js gradient rgba in `dashboard.js`); `Views/Shared/_Layout.cshtml.css` is leftover template scoped CSS, still bundled via `InternTrackAI.styles.css`. Tooltip/popover gotcha: Bootstrap re-declares `--bs-tooltip-*` on `.tooltip` itself, so bridge tokens there; the app does not use `data-bs-theme`. Sticky/fixed gotchas: the sticky element is `body > header` (a sticky `.site-nav` can't leave its same-height parent); its measured height is `--site-nav-h` (set by `site.js`), used by the Applications table header and `scroll-padding-top`. The Applications table header is sticky only from 768px, where `overflow: visible` removes the `.table-responsive` scroll container — so above that breakpoint a table wider than the viewport widens the *document*. Its columns bottom out at ~945px and the page only fits that from 992px, so Location, Mode and Match are `d-none d-lg-table-cell` (Match with a `d-md-none` step, because it is back at `sm` where the table scrolls again) and step out for the 768–991px band. Adding a column to that table means re-checking the band; `e2e` asserts on it in both the visual and compatibility dimensions. Entrance animations must not keep a transform after they end (`.anim-fade-up` uses fill-mode `backwards`): any retained transform on `<main>`, even `translateY(0)`, traps the drawer, bulk bar and modals (`position: fixed`) inside it and under the navbar. Chromium paints no outer `box-shadow` on table header cells; use an `inset` shadow or a pseudo-element.

**`--muted-2` is not a text colour.** At 1.9:1 light / 3.24:1 dark it cannot carry readable text, and no intermediate value fixes that: to reach 4.5:1 it would have to become #67676C / #98989D, which *is* `--text-2` — the tier would collapse rather than darken. So it is reserved for things that are not prose: status dots, the funnel bar, breadcrumb and chevron separators, the search icon, disabled `.page-link`, the `::placeholder` rules (transient hint text, every field has a real `<label>`) and Bootstrap's `--bs-tertiary-color` bridge. The 18 rules that used it for readable text — landing fine print and footer, `.auth-footnote`, `.quick-action-hint`, `.resume-ai-powered`, `.analyzer-model-tag`, the "+N more" counts, the dark `.badge-saved`/`.mini-stat-saved`, `.tour-count` — read from `--text-2` instead. Putting prose back on `--muted-2` re-breaks AA.

**`--accent-soft` vs `--accent-surface`.** `-soft` is a translucent wash for chips and badges sitting on `--card`. It does not work for a full-width box on `--bg`: any wash of a dark blue over a mid-grey only darkens it, so `--accent-text` landed at 4.17:1 there and no alpha fixed it (.05 still gave 4.48). `--accent-surface` is a solid tint *lighter* than `--bg` for that case (`.cl-info-banner`, `.lp-final-box`), clearing 4.94:1 for link text and 4.99:1 for body. In dark the wash already lifts off the background, so `--accent-surface` is just `--accent-soft` there.

The accent and secondary-text values are contrast-load-bearing, not taste: `--text-2`/`--muted` at #6E6E73 measured 4.38:1 on `--bg` (AA wants 4.5), and `--accent` at #0A84FF carried the white `.btn-primary` label at 3.65:1 in both themes. #67676C and #0066CC clear it (4.86 and 5.57); `--accent-h`, `--accent-soft`, `--accent-rgb` and `--focus-ring` moved with the accent so the palette stays one colour. Darkening either further, or lightening `--accent` back for a brighter dark theme, re-breaks AA — white on the fill is the binding constraint. `wwwroot/js/dashboard.js` reads `--accent`/`--muted` at runtime so charts follow automatically; **`Services/EmailTemplates.cs` does not** — its `Accent`/`Muted` literals are still #0A84FF / #6E6E73 and are the one copy left to bring in step.

Non-colour tokens: `--radius` 16px, `--radius-md` 12px, `--radius-sm` 10px, `--radius-pill` 999px, `--shadow-xs/-sm/-/-lg` and `--focus-ring` (both themes), `--ease`, `--duration` 180ms, `--font`.

**Guided tour.** Copy and targets live in `wwwroot/js/tour-steps.js` — the only file to edit for either; `tour.js` is the engine and knows nothing about individual steps. A target must be `#id` or `[data-tour="…"]`: class and descendant selectors fail `Integration/TourTests.cs` by design, because the tests verify each selector by string-matching the rendered page rather than pulling in an HTML parser. For the same reason `tour-steps.js` assigns a **strict-JSON** object literal (double-quoted keys, no trailing commas) — keep comments outside the object or the tests can't parse it. The `?` key is still the keyboard-shortcuts modal, not the tour; the tour is the "Tour" button in the nav (`_Layout.cshtml`, signed-in pages only). Auto-run is gated on `localStorage["itai.tour.v1"]`, never a user record — the demo account is shared, so a per-account flag would let the first visitor dismiss it for everyone.

**Dependencies.** No new NuGet packages, vendored libraries or CDN scripts without asking the user first.

**Working rules from the user.**
- Never edit `app.db` directly; data changes go through migrations or the app UI.
- Never change passwords or `EmailConfirmed` in the database; never create accounts outside the app's Register page. Verify with throwaway accounts registered through the UI, never the demo password.
- Don't trigger real OpenAI calls locally (a real key sits in user-secrets): run with the placeholder `OpenAI__ApiKey`, or a stub via `OpenAI__BaseUrl` for the five services that honour it. The rule covers automated and routine runs (tests, Playwright verification, seeding). Exception: a one-off comparison the user explicitly asks for, such as a prompt before/after, may use the real key, limited to the number of calls agreed, against a throwaway account seeded with the placeholder key so resume auto-fill makes no extra call.

## 12. Known gaps and deliberate decisions

Deliberate — do not "fix":
- `RequireConfirmedAccount = false`: registration signs you straight in and no confirmation email is sent. Password reset is the only email the app sends.
- The public profile (`/p/{slug}`, commit c155efe, migration `RemovePublicProfile`) and uploaded cover letters on the profile (bbb5f48, `RemoveUploadedCoverLetters`) were removed on purpose; profile Age too (`RemoveAgeFromProfile`). Don't reintroduce them. AI-generated cover letters are a separate, current feature.
- Skill gap role matching (`SkillGapService.MatchesRole`) is deterministic and literal-word based: a strict majority of the tag's non-filler words must appear in the role title after a fixed suffix table (`Stem`) and compound joining. No synonyms, role families, fuzzy distance or AI. Commit daf2533 relaxed it once, from "every word" to this strict-majority rule; that is the agreed rule. Do not loosen it further or add synonyms to make demo data split nicely — change the seed (`DemoSeeder.TargetRoles`) instead. Only Applied-or-later applications count; `"[]"` counts as analyzed; card hidden under 3 analyzed.
- Google OAuth consent screen stays in Testing mode (100 test users); only the `gmail.readonly` scope is ever requested; email bodies are never stored.
- Login lockout: `/Identity/Account/Login` passes `lockoutOnFailure: true` and Program.cs sets `MaxFailedAccessAttempts` 5 / `DefaultLockoutTimeSpan` 15 minutes, so five wrong passwords buy a 15-minute wait — a credential guard and a CPU guard both, since each attempt costs a 100k-iteration PBKDF2 hash. The `IsLockedOut` branch is live now: it re-renders the form with `LoginModel.LockedOutMessage`, which is built from the configured window so the stated wait can't drift from the enforced one, and points at password reset as the way out that doesn't involve waiting (`ForgotPassword` stays reachable while locked). **The shared demo account is the one exemption** — its password is handed out by the landing page, so any visitor could otherwise lock it for everyone; `Login.cshtml.cs` matches it through `ConfiguredAccounts.IsConfigured(..., DemoEmailKey)`, never a `==`, and passes `lockoutOnFailure: false` for it alone. Pinned by `Integration/LoginLockoutTests.cs` in both directions: four failures must not lock, five must, and the demo must survive twice the threshold. Accepted trade-off: the lockout message confirms an account exists to anyone willing to spend five failed attempts on one address — standard Identity behaviour, and unlike `ForgotPassword` (which must stay an identical-response endpoint) the cost of probing here is the point.
- Demo account: Gmail Connect refused, resume auto-fill skipped, tighter AI limit, Draft follow-up returns the canned `FollowUpService.DemoDraft` and refuses improve, and Rewrite a bullet returns the fixed `ResumeRewriteService.DemoVariants` (labelled as samples of `DemoSampleBullet`), all without taking a demo AI permit (`[NoAiCallForDemo]`). On Identity/Account/Manage, `DemoAccountGuardFilter` (registered in Program.cs on the whole folder) refuses every POST to credential pages (change password, set password, change email, delete account, all 2FA pages, external logins) with a redirect to Manage and a "Not available on the demo account." toast; ChangePassword and DeletePersonalData render read-only with the notice, the library pages redirect. Manage/Index renders read-only (display name form disabled, POST refused); `ProfileController.SaveInfo` refuses a demo display-name change (JSON `field: "displayName"`) and keeps the stored name when the disabled input is omitted. PersonalData stays open. `DemoAccountGuardTests.Every_manage_page_is_either_guarded_or_explicitly_allowed` fails if an Identity UI upgrade adds an unclassified page.
- Keyword coverage extraction is **deterministic, not a model call** — decided on evidence, not convenience. A prototype was run against the five real postings in the local `app.db` (Shopify 4446 chars, Microsoft 4194, MDA Space 1688, CIBC 1556, IBM 1462) and matched against a real resume PDF: it extracted 19–33 usable terms each (VHDL/FPGA/RTOS/CCSDS/I2C/JTAG for the embedded role, Terraform/GCP/Prometheus/Grafana for the DevOps one, ASP.NET/Node.js/Entity Framework Core/Spring Boot for the two SWE ones) with 1–2 junk chips per capped list of 15. A model call would buy marginally cleaner phrasing at the cost of a cache that must be invalidated whenever the active resume changes, a `[NoAiCallForDemo]` branch, rate-limit interaction and prompt-injection surface on untrusted posting text. Being free is what lets it run on every drawer open and stay uncached, which is what makes "always reflects the resume that is active right now" true by construction. Two failure modes are pinned by tests because they are the real ones: a posting written **without bullet glyphs** (a line opening with a cue word is a requirement, never a heading — getting this wrong silently swallowed every term on those lines), and a posting **flattened to one line** by the bookmarklet's HTML strip (still yields its technologies; only the requirements boost is lost, so ordering falls back to frequency).
- Keyword matching is **literal, on word boundaries**: a posting asking for "SQL" is not covered by a resume that only says "PostgreSQL". Substring matching would make "Java" match "JavaScript", and a false "you're covered" is worse than a false "you're missing this" because the user acts on it by not fixing anything. Real equivalences go through `SkillAliases` instead, which is auditable. One deliberate asymmetry: a term starting with a non-alphanumeric relaxes its *leading* boundary, so ".NET" is covered by "ASP.NET Core" — without it no .NET resume would ever cover it. Where the strict rule bites, `NearMiss` says so on the chip ("your resume has PostgreSQL…") rather than letting it look like a bug. Do not loosen this to substring matching.
- No status history: analytics use current status (Interview/Offer = response).
- Antiforgery failures and other 400s surface as 404 because status-code pages re-execute through `/Home/NotFound`.

Genuinely unfinished or known issues:
- Compare modal prints Status as the enum integer (`applications.js` reads `data-status`, rendered as `(int)item.Status` in `_Table.cshtml`).
- ForgotPassword now refuses the demo address before minting a token (checked on the typed address and on the resolved account). ResetPassword and ConfirmEmailChange are still ungated, but both need a token the demo account can't obtain — the change-email POST that issues one is refused by `DemoAccountGuardFilter`.
- `GET /Calendar/feed.ics` is anonymous and `UserProfile.CalendarToken` has no index, so every wrong token scans the table; a valid one loads that user's whole application list unpaged. The 32-byte token itself is not guessable.
- `Views/InterviewPrep/Prep.cshtml` still carries an inline script (~170 lines) not yet moved to `wwwroot/js`.
- `GmailConnection.LastHistoryId` is recorded but incremental `history.list` sync is not implemented.
- Skill caps on matcher output are prompt-only; no server-side validation of the JSON skill columns.
- `OpenAI:BaseUrl` is ignored by the analyzer, matcher, cover letter, interview prep and salary services.
- `Profile/RenameResume` lacks an ownership test.
- `GeneratedCoverLetter` XML comment claims letters survive application deletion; the controller deletes them.
- `ResumeMatcherService` is the one AI service that never got the prompt-hardening pass: it interpolates the resume and the job description straight into the prompt (`ResumeMatcherService.cs:74-91`) with no `PromptData` tagged sections, data-rule or tag-look-alike stripping, unlike `FollowUpService` and `ResumeRewriteService`. It also logs the **entire OpenAI error body** (`:118`), where `ResumeRewriteService.cs` deliberately logs the status code only because an error body can echo parts of the request. Both are known and deliberately deferred, not oversights — fix them together when the matcher is next touched.
