# CLAUDE.md

Guidance for Claude Code sessions in this repo. Every statement below was checked against the source on 2026-09-15; where something could not be verified from the repo it says so.

## 1. What this is

InternTrackAI is an AI-assisted internship/job application tracker for people running an internship search, replacing the spreadsheet: a pipeline of applications (list, Kanban board, detail drawer) plus GPT-4o-mini tools that fill forms from postings, score resume fit, write cover letters and interview prep, and turn Gmail messages into status suggestions. Portfolio project by Majd Arow, deployed on Railway.

- Live: https://interntrackai.majdarow.com (custom domain, canonical). The original https://interntrackai-production.up.railway.app is deliberately kept alive so old links and bookmarks keep working, so the app is served on **two** hostnames at once and nothing may pin either — every absolute URL comes from `Request.Scheme`/`Request.Host`, pinned by `ForwardedProtoTests.Every_absolute_url_follows_the_host_the_request_arrived_on`. In particular do **not** set `Google:RedirectBaseUrl`: the OAuth state cookie is host-scoped, so forcing a flow started on one host to return to the other loses the cookie and fails the callback. The one origin that *may* be pinned is `Email:BaseUrl` (emailed reset links), because a reset token is bound to the user and not to a cookie — see `Services/EmailLinkBase.cs`; it is unset by default, unset means the old behaviour, and it is set on the live service (§11).
- Shared demo account behind the landing page's "Try the live demo" button (`POST /Account/DemoLogin`, credentials from `Demo:Email`/`Demo:Password`). `Services/DemoResetService.cs` reseeds it nightly **only when `Demo__AutoReset=true`**; the code/appsettings default is `false`. The Railway value is not visible from the repo.

## 2. Stack and versions

- ASP.NET Core 9 MVC + Razor views (`net9.0`), ASP.NET Identity (scaffolded Razor Pages in `Areas/Identity`), EF Core 9.
- SQLite locally (`Data Source=app.db`); PostgreSQL in production. `Program.cs` switches to Npgsql when the `DATABASE_URL` env var is set (hand-parses the `postgres://` URI; SSL disabled for `*.railway.internal`, required otherwise).

- Gmail: Google.Apis.Gmail.v1 + Google.Apis.Auth. Email: Resend HTTP API, raw `HttpClient` (no SDK). Logging: Serilog (console). Hosting: Docker on Railway.

## 6. Services

OpenAI callers are marked **[AI]**. All read `OpenAI:ApiKey` and treat blank or `your-openai-api-key-here` as "not configured". Only `ProfileExtractorService`, `ResumeScoreService`, `FollowUpService`, `ResumeRewriteService`, `PracticeQuestionService`, `AnswerFeedbackService` and `OpenAiStatusClassifier` honour `OpenAI:BaseUrl` (stub endpoint for local verification); the analyzer, matcher, cover letter, **interview prep** and salary services hardcode `https://api.openai.com` and will reach the real endpoint even when a stub is configured (§12).

- `ConfiguredAccounts.cs` — the only way to read/match `Demo:Email` and `Admin:Email`: trims config values, compares ignoring case and whitespace, resolves users via `FindByEmailAsync` then `FindByNameAsync`. Used by DemoSeeder, DemoResetService, AdminController, AccountController, `AiRateLimiting.IsDemoEmail`/`IsDemoUser`, `DemoAccountGuardFilter` and the Manage page models (`IsDemoUser`, `DemoUnavailableMessage`).
- `AiRateLimiting.cs` — `AiRateLimitOptions`, singleton `AiUsageLimiter` (per-user fixed-window buckets), `NoAiCallForDemoAttribute`, and the `"ai"` policy + 429 handling. Registered via `AddAiRateLimiting` in Program.cs.
- `JobAnalyzerService.cs` **[AI]** — text or URL (fetches page via named client `UrlFetcher`, strips HTML, 8000 chars) → company, role, location, salary, skills, deadline, interview date. `AnalyzeAsync` is `virtual` with a CancellationToken so tests subclass it. Called by AnalyzerController, CaptureController.
- `ResumeMatcherService.cs` **[AI]** — resume text vs job description → score 0–100, tier (`RecommendationFor`: ≥60 APPLY, ≥40 MAYBE, ≥20 CONSIDER SKIPPING, else SKIP), matching/missing skills, strengths, summary. Static `ExtractPdfText` (PdfPig) is the PDF parser, now called only by `ResumeTextService`. Called by `ProfileController.AutoMatch`.
- `ResumeScoreService.cs` **[AI]** — job-independent resume score, strengths, improvements. `ProfileController.ScoreResume`.
- `CoverLetterGeneratorService.cs` **[AI]** — `GenerateAsync` (letter dated with the user's local today) and `ImproveAsync`. CoverLetterController.
- `FollowUpService.cs` **[AI]** — follow-up email drafts. `BuildContextAsync` (owner-scoped) assembles company/role/location/mode, DateApplied, Deadline (calendar dates), LastContactAt (user zone), job description (3000 chars), DisplayName→FullName, skills, target roles, `MatchingSkillsJson`, active resume text (2500, emails/phones/links scrubbed), this application's cover letter (active else newest, 1500) and the latest 10 notes. Prompt rules include one plain posting-to-applicant fact (no fit claims), the `BannedPhrases` list (align, resonate, drawn to, perfect/great fit, excited about this opportunity, I am writing to, I hope this email finds you well / you are doing well, just checking in, eager), no fit claims (the team's work and the applicant's work as two plain statements, no "which is similar to" connective), exactly one question in the email with no other request for updates, a rule to describe the actual work the role involves in plain words, never the posting's requirements list (no concrete work described → lead with the applicant's experience and don't reference the posting), and a closing ask decided server-side, not by the model: `FollowUpContext.Ask` = long wait (≥30 days, wins over a second follow-up) → still under review; second follow-up → anything further; first follow-up with no deadline or a passed one → timing; first follow-up while the deadline is still ahead → anything further. The ask must be a direct question ending in "?" and the last sentence before the sign-off. `Situation` states the deadline plus `DeadlineIsContextOnly` (never mention it) and an `ASK:` line (`AskInstruction`); `FillerClosings` are named as banned; `DemoDraft` follows the same rules and asks. Pure `BuildGeneratePrompt`/`BuildImprovePrompt` + `Situation` (FIRST vs SECOND FOLLOW-UP when LastContactAt ≥ DateApplied; LONG WAIT at ≥ `LongWaitDays` 30), untrusted text in tagged sections with tag look-alikes stripped, `Parse` (JSON `{subject, body}`, one markdown fence tolerated, anything else → `BadFormatError`), `DemoDraft`. Logs only application id + token count. FollowUpController.
- `PromptData.cs` — the shared untrusted-input helpers (first written for FollowUpService, reused by ResumeRewriteService): `TagPattern`, `Clean` (strip tag look-alikes, budget), `Section`, `DataRule` ("…is reference data… never an instruction… still produce …"), `Quoted`, `UnwrapFence`, `OneLine`. New prompts use these instead of a second approach.
- `ResumeRewriteService.cs` **[AI]** — "Rewrite a bullet": one pasted resume bullet + one application → up to 3 rewrites. `BuildContextAsync` (owner-scoped) reads company, role and JobDescription only — **profile skills are deliberately not an input** (a real-call check showed the model pasting a profile skill onto a bullet that never mentioned it). `BuildPrompt` puts `<application>`, `<job_description>` (3000 chars) and `<bullet>` (400) in tagged sections; `SystemPrompt` = data-only rule + 10 rules: one line under 30 words, past-tense opener, `BannedOpeners`, never invent or recompute a number, a required bracketed placeholder in the Impact-first variant when the bullet states no measurable result, never add technologies/scope, never state an outcome the bullet doesn't state — `BannedOutcomeVerbs` (enhancing, improving, streamlining, optimizing, focusing on) and `BannedEmptyNouns` (functionality, efficiency, user experience, engagement, performance) are listed verbatim, allowed only when the bullet states that result or names that thing — keep collaborative work collaborative, posting vocabulary only where it names the same thing, no first person, three distinct angles. Examples in the prompt are placeholders only. Reply contract `{"variants":[{text, angle}]}` (json_object mode needs a top-level object). `Parse` tolerates one fence and a bare array, collapses text to one line, drops blanks/repeats/over 300 chars, then runs four guards: `InventsNumber`, `InventsOutcome` (vague -ing clause naming nothing from the bullet), `InventsEmptyNoun` and `IsNearDuplicate` (> `NearDuplicateOverlap` 0.6 of the longer variant's distinct words — a Concise compression lands at ~50% and survives). **The floor is one variant**: survivors are returned with `Discarded` > 0 so the endpoint can add `DiscardedNote`; only an empty result is `InventedContentError`. The outcome/near-duplicate guards are lenient by design (the bullet's own verb, a placeholder-only clause, or any one bullet word passes `InventsOutcome`). `NormalizeBullet` strips leading glyphs. `DemoVariants` = fixed rewrites of `DemoSampleBullet`. Logs application id, kept and discarded counts, tokens only. ProfileController.RewriteBullet.
- `InterviewPrepService.cs` **[AI]** — 8–10 questions (`GeneratedQuestion` records, category already resolved to the enum). `GenerateAsync` is `virtual` so tests subclass it, same as `JobAnalyzerService.AnalyzeAsync`. The controller turns the results into `PracticeQuestion` rows; the service itself stores nothing. **`CritiqueAnswerAsync` was deleted in Phase 4** — one answer-feedback prompt in the app, not two; see `AnswerFeedbackService`.
- `PracticeQuestionService.cs` **[AI]** — practice generation and the three dedupe layers (§8 records which of them actually work). Honours `OpenAI:BaseUrl`, unlike the other generators, so the whole loop can be driven from a stub without spending. Over-requests by `OverRequest` (2) to absorb dedupe losses, and caps the top-up at `MaxTopUps` (1). Temperature 0.8 — variety is the product, and near-zero temperature is itself a cause of repetition.
- `PracticePrompt.cs` — the generator prompt, built in one place so it can be printed and asserted without a model call. `TopicRule` is the load-bearing part (it keeps topics precise enough for `TopicKey` to compare); the exclusion block is **measured not to steer** and is kept only because it is free.
- `TopicKey.cs` — **what actually deduplicates practice questions.** Normalises a topic (lowercase, strip punctuation, drop noun-phrase filler — `vs`, `between`, `for`, `strategies`, `techniques`, `implementation` — then sort tokens) and treats two topics as the same subject when their token sets are equal **or one contains the other**. Equality alone is not enough: of the four real collisions it was built from, two are equal after normalising and two are subsets (`Rate limiting implementation` ⊂ `API rate limiting`). Its stopword list is deliberately *not* `QuestionHash`'s — that one is tuned for question framing (what/how/why/explain), which never appears in a noun phrase. Known cost, accepted: a short topic blocks its supersets, so once "caching" is stored "caching invalidation" is rejected.
- `QuestionHash.cs` — the dedupe key behind the unique `(UserId, PromptHash)` index. `Normalize` lowercases, strips punctuation, drops the spec's question-framing stopwords and **sorts the remaining tokens**; `Of` is the hex SHA-256 of that. **It catches argument reordering, not paraphrase** — "difference between a mutex and a semaphore" vs "…a semaphore and a mutex" collapse, but "difference between a process and a thread" vs "how does a thread differ from a process" do not, because the shared idea is carried by different words. That boundary is deliberate and pinned by a test: paraphrase is the topic exclusion list's job (layer 1), hashing is the enforceable backstop. The spec offered the second pair as a token-sorting example; it is not one.
- `AnswerFeedbackService.cs` **[AI]** — **the app's only answer-feedback path**, used by both `/Practice/SubmitAnswer` and `/InterviewPrep/CritiqueAnswer`. Honours `OpenAI:BaseUrl`. Temperature **0.3**, against the generator's 0.8: this is a judgement, and the same answer submitted twice should not swing two points because variety was asked for. `EvaluateAsync` is `virtual` and the reply is parsed by `AnswerFeedback.FromJson`, which never throws — a reply that is JSON but the wrong shape still scores rather than erroring, because the user typed a paragraph and is owed feedback, not a formatting complaint.
- `AnswerFeedbackPrompt.cs` — the grading prompt in one place, printable and assertable without a model call, like `PracticePrompt`. **The answer box is the app's most inviting injection surface** — a large free-text field whose contents reach a prompt, with an obvious reward for succeeding (a 5) — so the question and the answer travel in `PromptData` tagged sections with the data-only rule and tag look-alikes stripped. `ScoringRule` defines all five bands verbatim and says "most real answers are a 2 or a 3": told only to "score 1-5", a model treats the number as a politeness dial and returns 4 for everything, which is the same lesson `PracticePrompt.DifficultyRule` records about difficulty. Behavioural questions get an extra instruction to judge structure. The question's `ModelHint` is passed in as what a strong answer was meant to cover.
- `AnswerFeedback.cs` — the parsed verdict: score (clamped 1–5, and a string `"4"` or `"4/5"` is read rather than discarded), strengths, **exactly two** improvements (padded with blanks the view skips, or truncated — a card whose shape is at the model's discretion looks broken the day the model returns five bullets), missing points, revised opening. Stored as JSON in `AiFeedback`; `Score` is duplicated into its own column because Phase 5's progress panel has to aggregate it in SQL. `ToPlainText()` is the flattening that keeps the prep page's `{success, feedback}` contract working.
- `AttemptHistory.cs` — reads and rotates `PriorAttemptsJson`, newest first, capped at `Keep` (3) for the same reason `ResumeParseService` prunes drafts to three. The feedback on a superseded answer is deliberately **not** kept: a retry wants "what did I say last time and did it go better", and storing three full critiques beside three full answers triples a column for the part nobody re-reads. Unreadable history is replaced rather than defended — losing an old attempt is a small cost, being unable to answer at all is not.
- `PracticeAnswerService.cs` — **the only path that writes an answer to a `PracticeQuestion`**, shared by both controllers. Validates → scores → rotates the attempt being replaced into history → writes the four answer columns. `MinAnswerChars` (40) is enforced **here**, not in the browser: the client disables its button as a courtesy, this is what stops three words costing a model call and the only check a scripted request meets. Nothing is written until the model has answered, so a retry into a quota error leaves the previous attempt exactly where it was. `EvaluateWithoutStoringAsync` is the fallback for a question that matches no stored row.
- `PracticeProgress.cs` — the practice page's progress card. **No AI**, and a pure `Build(rows)` like `KeywordCoverageService.Build`, so every number on the panel is unit-testable without a host. **Computed in C#, not as SQL aggregates, deliberately**: the weakest topic is a `GROUP BY` over a text column (collation — `C` locally, `en_US.utf8` in production, so a parity test would pass vacuously) and the average is `avg()` over a nullable int, which SQLite and Npgsql do not return as the same type. Aggregating in memory removes both questions rather than testing for them, which is what `ResumeAnalyticsService` (read rows, then `.Average()`) and `SkillGapService` (group with `StringComparer.Ordinal`) already do. Groups topics through `TopicKey.Of`, so "SQL query optimization" and "… techniques" are one average rather than two thin ones — `Of` (exact equality on sorted tokens) is the right primitive and `Collides` is not, because subset containment is not transitive and cannot partition anything. A trend arrow needs `MinAnswersForTrend` (20) answers: below two full windows there is no honest comparison, and an arrow off three answers is noise presented as a finding. `MinAnswersForWeakestTopic` is 3 — one bad answer is not a weakness.
- `SalaryInsightService.cs` **[AI]** — range + note from model knowledge (not live data). SalaryInsightController.
- `ProfileExtractorService.cs` **[AI]** — `IProfileExtractor`: resume text → a `ParsedProfile` **proposal** (name, field, category, seniority, years, location, skills **each with an evidence snippet and a confidence**, target roles, education, summary). The one service on **`json_schema` (strict)** rather than `json_object` — the reply is deep and nested and repairing a malformed one would be guesswork. Resume text goes in a `<resume>` section through `PromptData` with the data-only rule. **Deliberately carries no field context** (§8): it is what *produces* the field, and feeding the stored one back would make it self-confirming and hide a career change. `SystemPrompt` is public so `ProfileExtractorPromptTests` can pin the field-neutrality rules; `DemoParse()` is the canned **nursing** parse for the demo account (§12).
- `ParsedProfile.cs` — the proposal type and its reader. `FromJson` never throws and never trusts: an unrecognised category → `Other` and an unrecognised level → null (via `ProfileFields`), years clamped, lists capped and deduped, evidence collapsed to one line and truncated, and **a skill with no evidence is dropped entirely** — the prompt asks for that rule, this is what enforces it. `FromJsonOrEmpty` round-trips a stored draft so a column that no longer parses can't 500 the review screen. Unrecognised confidence is **Medium**, not Low: reading a typo as "low" would silently hide real skills.
- `ResumeParseService.cs` — resume text → a stored `ParsedResume` draft. **Never writes to the profile.** `PendingAsync`/`ByIdAsync` (owner-scoped) feed the review screen, `StoreDemoParseAsync` stores the canned parse with no model call, and every insert prunes to `MaxDraftsPerUser` (3). Rate limiting is the caller's job, as with `ProfileAutoFillService`.
- `ResumeFileType.cs` — what counts as a resume, decided **from bytes, never the filename**, plus the one place the two formats' extensions and media types are written. PDF is the `%PDF` magic number; a .docx is a ZIP, so the signature alone would accept any zip — `DetectAsync` opens the archive and requires a `word/document.xml` entry. A renamed `.exe` fails the first check, a renamed `.zip` fails the second. Leaves the stream rewound so the caller can still save the file.
- `DocxText.cs` — plain text from a .docx, the DOCX twin of `ResumeMatcherService.ExtractPdfText`; called only by `ResumeTextService`. Walks `Descendants<Paragraph>` so **table cells are read** — a large share of resumes lay their skills section out as a table, and a body-paragraphs-only walk drops every one of them without failing. A table row flattens to one line so the cells stay together.
- `ResumeTextService.cs` — **the only way to read a resume's text**, for both formats. Returns `ResumeTextResult(Status, Text)` with `ResumeTextStatus` = Ok / NoResume / FileMissing / Unreadable / NoText (`MinUsefulChars` 50, the floor the AI endpoints each applied before). Serves `ResumeVersion.ExtractedText` when set, otherwise parses the file once — PdfPig or `DocxText`, chosen by `ResumeFileType.FormatOf` — and writes it back; **the format branch lives here, not at any call site**. `LooksScanned` (`LikelyScannedChars` 200) is separate from the status: the file is fine and the upload succeeded, only the parse has nothing to work with, so only the parse says "it may be a scanned image". OCR is out of scope by decision. Never persists an empty string — a parse that finds nothing leaves the column null so it retries instead of poisoning the row — and a failed write-back still returns the text. `StoreAsync` is the upload-time call. Used by ProfileController (ScoreResume, AutoMatch, AnalyzeResume, UploadResume), CoverLetterController, InterviewPrepController, FollowUpService and KeywordCoverageService.
- `ProfileAutoFillService.cs` — **the only writer of AI output to a profile**, reached only from `ProfileController.ApplyResumeReview`. `ApplyAsync(userId, draft, reviewed)` takes a `ReviewedProfile` (what the user left checked), merges tags **add-never-remove** through `ProfileTags.Merge`, sets the scalars to the confirmed values, stamps `ProfileLastEnrichedAt`, and marks the draft applied in the same save. Refuses a foreign or already-applied draft. There is no path from the extractor to here that skips the review screen; adding one re-creates the silent overwrite this flow removed.
- `SkillAliases.cs` — the one alias map (Node.js, PostgreSQL/Postgres, CI/CD/CICD, Kubernetes/K8s, JavaScript/JS, TypeScript/TS, Go/Golang, React, C#, .NET/dotnet, AWS, REST APIs). `Map` (every lower-cased spelling → canonical display), `Canonical`, `Spellings`. `SkillGapService.Aliases` forwards to it; add new spellings here, never in a second copy.
- `KeywordCoverageService.cs` — "Keyword coverage", the ATS-style literal-term check. **No AI**, so no rate limit, no prompt, no demo branch and nothing cached. Pure `Build(jobDescription, resumeText, company, role, location)` → `KeywordCoverage(Available, Reason, Covered, Total, Missing)`; `Extract` pulls the posting's terms (punctuated tech tokens claimed first so `ASP.NET`/`CI/CD` never re-split, then acronyms, then capitalised runs that don't open a sentence, then cue-phrase captures), and `Present`/`NearMiss` do the matching. Terms count once per line; headings, month names, boilerplate and pay lines (`SalaryLine`) are dropped, as is a candidate containing an interior connective (prose, not a name). Noise rules tuned against branded program postings, which are far noisier than a requirements list: the employer's name is stripped from the front of a candidate when a real name remains ("Microsoft Azure" → Azure) and rejected outright when it isn't, `AddBrandNeighbours` grows the employer's words through name joiners so "Manulife/John Hancock" gives up both halves (plain adjacency deliberately does not, or Azure would vanish), `AddParentheticalAliases` treats an acronym and its bracketed expansion as one name in either order (but only when the bracket holds a single token, or "cloud platforms (IBM Cloud, AWS, or Azure)" would eat its own term), `CurrencyCodes` kills "CAD", two-letter tokens need to be in `ShortAcronyms` (so "AD" goes and "AI"/"ML"/"QA" stay), `RoleNouns`/`DegreeNouns` drop job titles and fields of study whether qualified or bare — you cannot add someone else's job title or a degree you don't hold — and because the capitalised run caps at three words, a run followed by a role noun is dropped with it so "Full-Stack Software Engineer" leaves neither half behind. `AddressLine`/`StreetTypes` and `AuthorizationLine`/`Nationalities` drop office addresses and right-to-work lines; "Drive" and "Way" are deliberately not street types ("Google Drive"). Ordering is frequency + 2 under a requirements heading, ties alphabetical. `MaxMissing` 15 caps the list but not the `Total`; `MinTerms` 10 is the "too short" floor. Reasons: `NoDescription`, `NoResume`, `UnreadableResume`, `TooShort`. JobApplicationsController.KeywordCoverage.
- `UserContextBuilder.cs` — `IUserContextBuilder` (scoped), **the one place the field context in an AI prompt is built**. `BuildAsync(userId)` reads `UserProfiles` and returns the `USER PROFILE CONTEXT` block (Field, Seniority, Location, Skills, Target roles); `Build(profile)` is the pure half the tests use, and `Prefix(block)` is how a prompt embeds it (block + blank line, or nothing). Two rules the shape depends on: **a line is emitted only when it has a value** (an empty label reads to the model as "blank", not "unknown"), and **no `Field` means the single `UnspecifiedFieldLine` and nothing else** — a half-filled block with skills but no field is what pushes the model back to its software-engineering default. Free text goes through `PromptData.Clean` against the union of the section tags used by the prompts that embed it, so a profile field can't close a section it sits inside. No profile row → `""`.
- `ProfileFields.cs` — parsing, bounding and display text for the field-awareness columns. `ParseCategory` (blank → null, unrecognised → `Other`, because something was clearly meant), `ParseSeniority` (blank or unrecognised → null, because guessing a level changes how every prompt pitches), `Years` (clamped 0–60), `Text` (trim, null for blank, capped at `MaxTextLength` 80), `Display` for the two-word enum members, and `Label(field, category)` → `"Registered Nursing (Healthcare)"` — the one wording, shared with `FollowUpService`. `TryParseName` matches **by name only**: `Enum.TryParse` otherwise reads "5" as `Healthcare`, and a number arriving where a name belongs is a broken client, not a choice.
- `TargetRoleSeeds.cs` — singleton; loads `Data/Seeds/target-roles.json` once into a `FieldCategory` → roles map for the profile page's role combobox, replacing the hardcoded software-engineering array that used to sit in `profile.js`. Keys that aren't enum members are skipped (that's how the file carries its own `_comment`), and a missing or malformed file logs a warning and leaves the map empty — suggestions are a convenience and free text always works, so this is never fatal. `All()` feeds the `#roleSuggestionsData` island.
- `ProfileTags.cs` — the single definition of "same tag" (trim, collapse whitespace, case-insensitive, first casing wins); JSON helpers. Mirrored client-side by `wwwroot/js/tag-input.js`.
- `ReminderService.cs` — the only place for "needs attention" rules: Overdue (deadline passed, still Saved), DeadlineSoon (≤7 days, not Offer/Rejected), FollowUpDue (Applied, anchor = later of DateApplied/LastContactAt, ≥ `FollowUpAfterDays` 3–30 default 7, not snoozed), UpcomingInterview (≤14 days). Snooze = 3 days. Used by HomeController (Attention card), JobApplicationsController (list filter, board/drawer chips via `ViewBag.AttentionById`, mark contacted/snooze), ProfileController (window bounds). The calendar feed does not use it; `IcsBuilder` emits raw dates.

- `UserClock.cs` — `UserClock` (pure UTC↔zone conversion + formatting) and scoped `UserClockProvider` (per-request cached; `ForUserAsync` for the anonymous feed). Injected into every view as `Clocks`.

- `ResumeAnalyticsService.cs` — "Resume performance": per resume version, sent (status ≠ Saved), responses (currently Interview or Offer), rate, low confidence under 5; card shows at ≥ 2 resumes. HomeController, ProfileController.

- `DemoProfileReset.cs` — the **narrow** demo reset: the shared demo profile's own fields, its `ParsedResume` drafts and its `PracticeQuestion` rows, and nothing else. Exists because the demo's review screen shows a nursing parse on purpose, and applying it writes clinical skills and a Healthcare field onto a profile whose 15 seeded applications are all software; leaving that to the nightly `DemoSeeder` left a window of up to 24 hours. Keyed by `PasswordResetLimiter.IpKey`, so "one client" means the same thing on both anonymous endpoints. Unlike ForgotPassword there is no oracle to protect: Register already has to say "that address is taken".
- `PasswordResetRateLimiting.cs` — `PasswordResetRateLimitOptions` (`RateLimiting:PasswordReset`: `PerIpPerHour` 5, `PerAddressPerHour` 2, `WindowMinutes` 60) and the singleton `PasswordResetLimiter`. Same built-in fixed-window primitive as `AiUsageLimiter`, but permits are taken **inside the ForgotPassword page**, not through the `"ai"` HTTP policy: that policy answers with a 429 and a toast, and this page must answer a refusal with the identical confirmation or the limit becomes the account oracle. `Allow(ip)` runs before the account lookup so probing costs the prober; `AllowSendTo(email)` runs only when a message is about to go out so probes can't burn a real user's allowance. ## 7. Data model

All app tables key on `UserId` (Identity user id string) **without** an FK to `AspNetUsers`; account deletion goes through `UserDataPurger`. Enums are stored as ints — never reorder members of `ApplicationStatus` (Saved, Applied, Interview, Rejected, Offer), `WorkMode` (Remote, Hybrid, OnSite) or `SuggestionState` (Pending, Accepted, Dismissed). **Ints, not strings, is the convention for new enums too, but a new enum must write its values out explicitly** — `FieldCategory` (Technology = 1 … Other = 13) and `SeniorityLevel` (Student = 1 … Senior = 5) do, so a member can be appended anywhere in the list without shifting rows already stored, and no member is 0 (an int column defaulting to 0 would read back as a real member). Append with the next unused number; never renumber or reuse one. `ProfileFieldsTests.The_stored_enum_values_are_pinned_so_appending_a_member_can_never_shift_them` fails if someone does. `ApplicationDbContext.ConfigureConventions` tags every `DateTime` as UTC on read and write (relabel, no shift).

## 8. Cross-cutting rules

**Ownership.** Every action taking a record id loads it with `Id == id && UserId == currentUser` and returns `NotFound()` (JSON `{success:false,error}` for fetch endpoints) on a miss — never 403, and never a silent no-op. 404 makes "not yours" indistinguishable from "doesn't exist", so ids can't be probed. Bulk endpoints silently ignore foreign ids. Foreign ids in bodies (e.g. `applicationId` on cover letter Save, `ResumeVersionId` on Create/Edit) are rejected or dropped. Every new id-taking endpoint gets a test in `tests/InternTrackAI.Tests/Integration/OwnershipTests.cs` (or the feature's endpoint test file).

**Configured accounts.** Never read `Demo:Email`/`Admin:Email` with `config[...]` or compare them with `string.Equals`/`==`; go through `Services/ConfiguredAccounts.cs`. Railway variables can carry surrounding whitespace, which Identity's lookups don't trim, and a LINQ `u.Email == x` is case-sensitive on both providers. Look users up only through `UserManager` (normalised columns). Callers today: `AiRateLimiting`, `DemoAccountGuardFilter`, the Manage page models, `DemoSeeder`, `DemoResetService`, `AdminController`, `AccountController` and `ForgotPassword`.

**Rate limiting.** **Two buckets, not one** (`Services/AiRateLimiting.cs`), because practice and everything else have opposite shapes — one practice round is 1 generate plus 5 scores, while resume parsing is rare and expensive. Sharing one allowance meant a demo visitor could not finish a single round before locking the whole app, and the 429 read as "the site is down" when cover letters and resume tools were fine.

| policy | actions | demo | signed-in |
|---|---|---|---|
| `AiRateLimiting.PracticePolicyName` (`"ai-practice"`) | `PracticeController.GenerateMore`, `SubmitAnswer` | 25 / hour | **100 / rolling 24h** |
| `AiRateLimiting.PolicyName` (`"ai"`) | everything else | 10 / hour | 20 / hour |

Both buckets are configured under `RateLimiting:AI` — the flat keys for the default bucket, `RateLimiting:AI:Practice:*` for practice — so there is **one section to read when debugging a 429**. Partitioned per user id (IP for anonymous, which `[Authorize]` normally turns away first); `AiUsageLimiter.KeyFor` prefixes the practice key so the two never collide. The 429 names which bucket was hit and, for practice, says what still works.

**"Per day" means 24 hours from that user's first practice call — not calendar midnight.** The signed-in practice allowance is a 1440-minute fixed window, and .NET's fixed-window limiter counts from the moment a partition is created. So a visitor who practises at 09:00 and one who practises at 21:00 have days that start twelve hours apart, neither aligned to a date or to an OpenAI billing day, and **a deploy hands everyone a fresh allowance** because the buckets are in-memory. `FixedWindowRateLimiterOptions` has no anchor, and since the buckets already reset on restart a calendar-aligned window would look exact while being no more durable — honest rolling was chosen over false precision. Do not reason about this number against a calendar day.

**Limits and windows are captured when a partition is first created and never re-read**, because the factory runs once per key. Changing `RateLimiting:AI:*` at runtime affects only users who have not called yet; in practice a config change needs a restart. Rejection: 429 + `Retry-After`; JSON `{success:false, hasResume:true, rateLimited:true, error}` for JSON/XHR callers, otherwise redirect to the local referrer with an error toast. Work outside a request draws from the same `AiUsageLimiter` bucket: each Gmail classification, and resume-upload auto-fill. Every new OpenAI call must be tagged `[EnableRateLimiting(AiRateLimiting.PolicyName)]` or take a permit manually. `[NoAiCallForDemo]` on an "ai" action makes the policy hand the demo account a no-limit partition there; use it only when the action's demo branch returns before any model call (today: FollowUp Generate/Improve and Profile RewriteBullet, pinned by `RateLimitTests.Demo_permit_exemption_is_only_on_the_reviewed_canned_actions`). Resume auto-fill skips its manual permit for the demo account in `ProfileController.AutoFillToastAsync`, and the demo can't connect Gmail, so no other demo path draws a permit without an AI call.

**Coverage audited 2026-09-21: all 12 AI services, every path.** Ten are policied through their controller action, and two take a permit by hand — `ProfileController.UploadResume`'s auto-parse (unpolicied on purpose: the policy's non-XHR rejection redirects the form post away, which would cost the user their upload instead of their parse) and each Gmail classification in `GmailSyncService` (line ~165), which is what covers the background hosted service. `ResumeParseService.ParseAsync` is the only model-calling method on its service and is reachable only from those two. `RateLimitTests.The_actions_behind_the_ai_policy_are_the_reviewed_set` pins the policied set; it sees attributes, not model calls, so **check for a manual `TryAcquire` before concluding an absent action is unlimited**.

**One honest limit of the in-memory design, accepted — and one that looks like a limit but is not.**

*The real one:* `AiUsageLimiter` is a singleton holding a `PartitionedRateLimiter`, so **buckets reset on restart** — a deploy hands every user a fresh budget. Restarts are owner-initiated or crash-triggered (`restartPolicyMaxRetries = 3`); an abuser cannot force one, so the practical effect is "the budget resets when you deploy".

*The one that is not:* buckets are per instance, which would matter only if the service could run more than one. **It cannot.** The live service is a single instance in EU West, and that is **structural, not configuration**: Railway does not allow replicas on a service with an attached volume, and `interntrackai-volume` is attached for `UPLOADS_PATH` (§11). So a per-instance bucket *is* an application-wide bucket here, by construction. Confirmed by the maintainer 2026-09-21; not verifiable from the repo. **Do not re-raise this as a scaling risk** — but see the coupling it creates, below.

*The coupling worth knowing:* that guarantee is held up by the volume, and the volume exists because uploaded resumes are stored on local disk. **Moving uploads to object storage would remove the volume, which would make replicas possible, which would silently multiply every user's AI budget by the replica count.** Nothing would fail; the app would just spend more. Anyone doing that migration has to give `AiUsageLimiter` a shared backing store in the same change, and at that point the spec's DB-backed cap becomes the right answer after all.

The spec's fix for both was a DB-backed per-UTC-day cap; that was **dropped deliberately** (2026-09-21) because at one instance it would be a second limiter over the same budget, and two limiters disagreeing about one wallet is worse than one that resets on deploy.

**Per-IP limiting already exists but is unreachable, and that is fine.** The policy's partition key is `userId ?? "ip:" + RemoteIpAddress`, so anonymous callers are bucketed by IP — but every AI endpoint is `[Authorize]`, so the fallback never fires. The spec asked for per-IP as "a second layer against unauthenticated abuse"; there is no unauthenticated AI surface to abuse. The adjacent real threat is account farming, and `RegistrationLimiter` already caps that at 5 accounts per IP per hour, which bounds one IP at roughly **5 × `PermitLimit` = 100 AI calls/hour** sustained. Recorded so it is not rediscovered as a gap.

**Outbound HTTP timeouts.** Every AI client registration in Program.cs ends with `.AiTimeout()` (`AiHttpDefaults`, 30s). Without it a typed client inherits `HttpClient`'s **100-second default**, which nobody chose and which is the same order as Railway's `healthcheckTimeout`: a hung OpenAI connection would hold the request, and the user's spinner, for the better part of two minutes. `max_tokens` is set on all 12 AI calls (200–2000), so a normal reply lands in seconds and 30s only ever catches a call that has already gone wrong. `Integration/AiHttpTimeoutTests.cs` is the guard and **auto-detects new clients**: it reflects over every type in the app assembly constructed with an `HttpClient` and fails any whose client still has the 100-second default, so a thirteenth AI service is checked without anyone remembering to add it. It skips a type nothing resolves to, which is how `ResendEmailSender` — registered only when `Resend:ApiKey` is set — stays out of it locally. Non-AI clients set their own: Resend and GitHub 10s, `UrlFetcher` 15s, and `CaptureController` caps its analyzer call at `Capture:AnalyzeTimeoutSeconds` (15) because a bookmarklet has a person waiting on a redirect.

**Anonymous endpoints that mint something.** Registration and password reset are both anonymous and both hand out something scarce (an account, an email), so each carries its own per-client fixed-window bucket taken *inside the page model* — `RegistrationLimiter` and `PasswordResetLimiter`, both keyed by `PasswordResetLimiter.IpKey`. The `"ai"` HTTP policy is the wrong tool for either: its rejection path redirects a form post to the referrer with a toast, which reads as the form losing the visitor's input. `Register` answers a refusal with the form plus the reason under a 429; `ForgotPassword` answers with the identical confirmation it shows on success, because there the refusal must not become the oracle.

**Email.** One seam, `IAppEmailSender` (`Services/EmailSender.cs`), backed by `ResendEmailSender` when `Resend:ApiKey` is set and `ConsoleEmailSender` otherwise; `IEmailSender` is registered onto the same choice because Identity UI's compiled pages resolve it. Bodies belong in `Services/EmailTemplates.cs`, never inline in a page model, and always ship an HTML and a text part. The origin of any link in an email goes through `Services/EmailLinkBase.cs`, so a deployment can take the request out of that decision with `Email:BaseUrl`. Two rules a new email must not break: **a send failure never changes what the user sees** (senders log and return rather than throw, so a page can't become an account oracle), and **nothing identifying is ever logged** — not the recipient, the body or the link, and provider error text goes through `ResendEmailSender.Redact` first because Resend echoes the recipient back. Anything emailed to `Demo:Email` is refused before a token is minted. **Any anonymous endpoint that can send must be limited or switched off**, and a refusal must be indistinguishable from a send: `ForgotPassword` carries `PasswordResetLimiter`, and `/Account/ResendEmailConfirmation` — which Identity UI maps, anonymous, backed by `IEmailSender`, and which really did turn 12 posts into 12 sends — is 404'd by `Areas/Identity/UnusedIdentityPageFilter.cs`.

**Security headers.** Kestrel's `Server: Kestrel` banner is off (`builder.WebHost.ConfigureKestrel(o => o.AddServerHeader = false)` in Program.cs, pinned by `SecurityHeaderTests.Kestrel_does_not_advertise_itself` — asserted on the option because TestServer is not Kestrel). `Services/SecurityHeaders.cs` is the one place the remaining headers' values are written; `app.UseSecurityHeaders()` sits directly after `UseForwardedHeaders` and **above `UseStaticFiles`**, which short-circuits — register it any lower and CSS, JS and uploaded files go out bare. Every response, static files / `/health` / redirects / the re-executed 404 included, carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: strict-origin-when-cross-origin`. The CSP ships as **`Content-Security-Policy-Report-Only`**, never enforced, because `_Layout.cshtml` (theme pre-paint, toast, shortcuts) and `Views/InterviewPrep/Prep.cshtml` still carry inline scripts — and for the same reason `script-src` is `'self'` with **no `'unsafe-inline'`**: the browser console reporting each remaining inline block is the list to work through before this can be enforced, and granting `'unsafe-inline'` would silence the report without changing the exposure. The policy names the only third-party origin in the app (Google Fonts, `fonts.googleapis.com` + `fonts.gstatic.com`) and `img-src blob:` for the profile photo preview in `profile.js`; `form-action 'self'` is safe for Gmail OAuth because Connect leaves by a 302, not a form post, and jsPDF's `doc.save()` is untouched by any directive. Headers are written in `Response.OnStarting` so they win at flush time regardless of pipeline order. Adding an origin, or enforcing the policy, means changing that one file and `Integration/SecurityHeaderTests.cs`, which pins the values on an MVC page, an Identity page, `/health`, a static file, an authenticated page, a redirect and the 404. There is no `report-uri`/`report-to` endpoint: violations surface in the browser console only.

**Forwarded headers.** Railway terminates TLS and forwards plain HTTP. `UseForwardedHeaders` (For, Proto, Host) must stay the **first** middleware, `ForwardLimit` stays **1**, and `KnownNetworks`/`KnownProxies` stay cleared: the defaults trust loopback only, Railway's proxy connects from a private address, and the headers were silently ignored (Gmail `redirect_uri_mismatch`, http:// reset links). All absolute URLs come from `Request.Scheme`/`Request.Host` (Gmail redirect URI unless `Google:RedirectBaseUrl` is set, password-reset links unless `Email:BaseUrl` is set, bookmarklet code, calendar feed URL) and must come out https in production — guarded by `Integration/ForwardedProtoTests.cs`. `ForwardLimit = 1` is written out explicitly rather than left to the default because both per-client rate limiters depend on it: the middleware consumes exactly one `X-Forwarded-For` entry and takes the **rightmost**, so a client-supplied value sits to the left of the one Railway appended and is discarded. Raise it and a caller can pick their own bucket — `ForwardedProtoTests.Only_the_last_forwarded_for_entry_is_trusted` pins this behaviourally (reading the option back would not, since the options object is passed to `UseForwardedHeaders` rather than registered in DI). `UseHttpsRedirection` runs only in Development (it would loop behind the proxy).

**Field context in AI prompts.** The app is not IT-only: a nursing, accounting or trades user must get their own field's language out of every AI feature. **Every AI prompt carries the field context, and it is built in exactly one place** — `IUserContextBuilder.BuildAsync(userId)` (`Services/UserContextBuilder.cs`) — never by interpolating profile columns into a prompt directly. The **controller** builds the block and passes it down as a trailing `string? profileContext = null`; the prompt services stay database-free, which is what keeps their prompt builders unit-testable. Embed it with `UserContextBuilder.Prefix(profileContext)`, never by hand. Wired today: `JobAnalyzerService`, `ResumeMatcherService`, `CoverLetterGeneratorService` (generate + improve), `ResumeScoreService`, `SalaryInsightService`, `InterviewPrepService` (generate + critique). Three deliberate exceptions: **`FollowUpService`** already assembles its own rich context, so it carries a single `Field:` line inside `BuildContextAsync` (via `ProfileFields.Label`, the shared wording) instead of the block; **`ResumeRewriteService` gets nothing** — §12 records why profile skills are kept out of it, and the block is profile skills; and **`ProfileExtractorService` gets nothing**, because it is what *produces* the field. Feeding the stored one back would make the parse self-confirming and stop a career change ever being detected — a nurse retraining into software would keep parsing as a nurse forever. A new prompt must also stay field-neutral in its own wording: no "technical skills", "codebase", "tech stack" or "engineering team", and no example role title (one in `ProfileExtractorService` pulled the model toward software titles on resumes with no software on them). The `Field` line is what makes output domain-specific; baked-in nouns only fight it.

**Practice question dedupe — the spec's model of this is backwards, and it was measured.** The spec describes three layers: topic steering in the prompt "does ~80% of the work", with hashing as a backstop. **Two instrumented live runs (2026-09-21, 12 real API calls, `LiveDedupeProbe`) show the reverse.**

| | what the spec claimed | what the runs measured |
|---|---|---|
| Layer 1 — topic exclusion list in the prompt | does ~80% of the work | **does not steer.** The model reused a topic string *verbatim* while that exact string was in its prompt, and produced the same ORM-vs-raw-SQL question in four of six batches |
| Layer 2 — mechanical rejection | a backstop | **carries dedupe almost entirely.** `TopicKey` caught 4 repeats in 30 questions |
| — of which `QuestionHash` | the mechanism named in the spec | **fired 0 times in 84 questions.** Real repeats are paraphrases, which it cannot see |
| Layer 3 — top-up retry | — | **never fired live.** See below |

**The scale rewards *lived* specificity, not *technical* specificity — measured, and it is the 3-band working as written.** Two production answers reported as under-scored were re-run verbatim (2026-09-21, 2 calls) and reproduced **3/5 each**, matching production. Both are excellent on mechanism — "with types the compiler finds every call site", "cover the empty string, whitespace, and the malformed case", Testing Library, `any` under deadline pressure — and neither contains anything the candidate personally did. The model said so directly: *"No concrete anchor or personal experience was provided to support your claims"* and *"You could have included a brief example of a real-world scenario where you applied these testing principles."* That is `ScoringRule`'s 3-band verbatim: *correct and relevant, but generic … no concrete detail of their own.*

**This is decided, not an open tension — do not "fix" it.** One of those questions was "in your opinion, what are the advantages of TypeScript over JavaScript", which asks for a view rather than a war story, so marking it down for lacking personal experience looks arguable on paper. It was considered and kept (2026-09-21): an interviewer asking for an opinion still wants to know where the opinion came from, and *"no concrete anchor or personal experience"* is true and useful feedback even on an opinion question. A good technical answer scoring 3 is the rubric working.

**What would justify revisiting it is usage, not inspection.** The trigger is *real practice repeatedly producing good answers stuck at 3 in a way that reads as unfair rather than instructive* — an observation you can only make by using the app over time. **Reading `ScoringRule` cold and finding it harsh is not the trigger**, and neither is a single surprising score; both have already happened here and the measurement said the scale was right. If it is ever revisited, the lever is `ScoringRule`'s 3/4 boundary, **not** `ConcreteAnchorRule` — the anchor rule is a floor and was measured not to move the top of the scale — and it needs a probe across both opinion-shaped and experience-shaped questions, because raising opinion answers to 4 risks taking genuinely generic ones up with them.

**Re-measured after deploy (2026-09-21, 3 calls): `ConcreteAnchorRule` raised the floor, it did not move the scale.** Two production answers with real specifics scored 3/5, which looked like the "harsher not stricter" failure. Re-running the recorded fixtures against the deployed prompt reproduced the baseline exactly — junk **2/5**, specific **4/5** — so the scale is where it was. A third, deliberately specific answer scored **3/5** with the model naming why: it never answered the *when/when-not* the question asked. **The rule sets a floor ("no anchor → at most 2"), not a ceiling**: a specific answer still has to clear the 4-band, which asks for an answer an interviewer would be satisfied with. A specific answer that does not address what was asked is a 3, and that is correct. Do not "fix" this without re-running the probe first; the measurement said the scale is fine.

**Refined 2026-09-21 by a second measurement, on answer scoring.** "Prompts do not steer" was too broad. The sharper rule is: **a prompt asking the model to *judge* does not land; a prompt naming a condition it can *check* does.**

A production smoke test found a junk answer — four fluent sentences, zero specifics, plus one bare claim — scoring **3/5**, with "What worked" crediting it for "acknowledging that both approaches have advantages and disadvantages". `LiveScoringProbe` scored the same two answers under three prompts, 6 real calls:

| prompt | junk answer | genuinely specific answer |
|---|---|---|
| original | 3/5 | 4/5 |
| prose tightened around the 2/3 boundary ("find the specific thing that earns a 3", "most answers are a 2 or a 3") | **3/5 — no movement** | 4/5 |
| `AnswerFeedbackPrompt.ConcreteAnchorRule` ("scan for a number, date, named tool, named role, or a situation that happened; none → **at most 2**") | **2/5** | **4/5** |

Both halves matter. A prompt that lowers every score is miscalibrated, not strict, and only the specific answer — holding at 4/5 — separates the two. The rule is appended **last, after the JSON contract**, because that is the position it was measured in; tidying it into `ScoringRule` is a change that needs re-measuring, not a refactor.

**So before writing more prose at a model, ask whether the instruction reduces to something it can look for.** If it does, say that instead. If it does not, expect it to be ignored and reach for a mechanism.

**If you are here to reduce repetition, reach for `Services/TopicKey.cs`, not the prompt.** That is the whole point of recording this: the spec's framing sends you to tune prompt wording, and prompt wording is the thing that was shown not to work.

Three supporting findings, all from the same runs:

- **Topic granularity held at every batch.** No "databases"-style labels appeared even at batch six, so `PracticePrompt.TopicRule` *is* earning its length — just at a different job than exclusion. Precise topics are what make `TopicKey`'s comparison possible at all, so don't strip that rule while deleting the exclusion block.
- **The failure is recurrence of a small set of high-salience topics, not saturation.** Rejections per batch were `[0, 1, 0, 2, 1, 0]` with no upward trend while the exclusion list grew from 0 to 25 topics. A context-dilution problem would get worse late; this doesn't.
- **Moving the exclusion list to the end of the prompt changed nothing measurable** (~6 topic collisions before, 5 after). It is still there because it costs nothing, not because it helped.

**Manufactured praise is filtered mechanically, and the filter is narrower than the problem.** `Services/EmptyPraise.cs` drops a "strength" made entirely of platitude — the production failure above and its family ("pros and cons", "shows an understanding", "covers the basics") — in the shape of `ResumeRewriteService`'s `InventsOutcome`/`InventsEmptyNoun` guards. **It fires only when the whole sentence is filler**, so a strength naming anything of the candidate's own survives; dropping a real strength is worse than keeping a weak one, and an answer with nothing working simply gets no "What worked" section, which is the truth about it. Its limit is recorded because the same probe run showed it: under the anchor rule the model returned *weak but not vacuous* strengths ("You mention Agile as a preferred approach"), which the filter correctly leaves alone. **It is a floor on the worst case, not a quality bar.**

**Caveat: n = 6 batches per run.** These are directionally clear but thin. Don't treat the numbers as precise, and re-run the probe before making a decision that depends on them.

**Accepted residual: semantic near-misses, roughly 1–2 per 30.** "SQL vs NoSQL trade-offs" and "NoSQL vs PostgreSQL" are the same question and `TopicKey` cannot see it — different tokens, neither a subset. Closing it means embeddings: an API call per batch, a similarity threshold nobody can tune except by guessing, and a false-positive class that silently withholds fair questions. Not worth it for a practice page. **Decided, not overlooked.**

**Layer 3 (top-up) is untested in production.** It is covered by tests against a scripted model, but across both live runs it never fired once: over-requesting by `OverRequest` (2) covered every shortfall. Treat it as unexercised rather than working, and if a change makes shortfalls common, verify it live before relying on it.

**Migrations.** `dotnet ef migrations add` scaffolds against SQLite: DateTime columns come out `type: "TEXT"` (on Postgres that becomes a `text` column: inserts coerce, every read throws `InvalidCastException`), **`bool` as `INTEGER`** (int4 on Postgres, which Npgsql refuses to read as a bool — `FixPostgreSqlTypesAndAddDataProtection` had to go back and repair eight columns), `double` as `REAL` (float4 on Postgres), and new tables get only `Sqlite:Autoincrement`, so Postgres inserts fail with 23502. Rule: every migration that adds/alters a DateTime, **boolean**, floating-point or identity column must branch on `migrationBuilder.ActiveProvider == "Npgsql.EntityFrameworkCore.PostgreSQL"` (`timestamp with time zone` / `boolean` / `double precision` vs `TEXT` / `INTEGER` / `REAL`) and add `.Annotation("Npgsql:ValueGenerationStrategy", NpgsqlValueGenerationStrategy.IdentityByDefaultColumn)` to new identity keys. Templates: `20260913230212_AddStatusSuggestions.cs` (dates + identity), `20260920191847_AddParsedResumes.cs` (dates + identity + bool). **The one shape that needs no branch is a nullable string column added to an existing table** — `text` on both providers, no table rewrite, no default backfill — which is why `AddPriorAttemptsToPracticeQuestions` chose `PriorAttemptsJson` over an attempts table. Its `type: "TEXT"` is still load-bearing (see below); the branch is what it skips, not the type. Verify with `tests/InternTrackAI.Tests/MigrationColumnTypeTests.cs`, which replays all migrations through the Npgsql SQL generator (no DB). `Every_column_lands_on_a_PostgreSQL_type_that_matches_its_CLR_type` is the general guard: it checks **every** column against the `CorrectPostgresTypes` table and **fails on a CLR type the table has never seen**, so a family nobody thought of (decimal, Guid, byte[]) can't slip through the way bool did — add a row and state what PostgreSQL should use. `No_app_column_becomes_a_length_limited_varchar_on_PostgreSQL` pins the other half: the `type: "TEXT"` every migration sets is **load-bearing**, because it overrides `[StringLength]` and keeps those columns `text`. **Provider parity.** The migration guard reads generated DDL, so it sees column *types* and nothing else. It cannot see how a database sorts text, folds case or rounds a timestamp — and both provider bugs this repo has hit were of that second kind. `Integration/ProviderParityTests.cs` covers that gap for the handful of queries where SQLite and Npgsql can legitimately disagree: it runs the same seed and query on both and asserts they agree, skipping the PostgreSQL half (and saying so) when the env var is unset. It is deliberately **not** a second copy of the suite — `TestAppFactory` stays SQLite-only. Add a case when a new query depends on collation, case folding, sub-second time, float width or a text index. Two rules for writing one, both learned the hard way:

1. **The local Postgres is not representative of production for anything collation-sensitive.** It is `C`; production is `en_US.utf8`. Any parity test whose answer depends on collation — text ordering, `LIKE`, `GROUP BY` or `DISTINCT` over text, a unique index on a text column — **passes vacuously here** and tells you nothing about production. Where that is the risk, remove the dependency in the query (`lower()`) rather than trying to test for it, and where a test must cover it, force the collation explicitly on the PostgreSQL side (`ProviderParityTests.Sorting_applications_by_company_gives_the_same_order_on_both_providers` does this, discovering the collation name at runtime because the same locale is `en_US.UTF-8` on macOS and `en_US.utf8` on Linux) instead of trusting the server's default.
2. **Assert an absolute expected value**, not just agreement, wherever the answer would otherwise be the database's choice. A parity-only assertion passes whenever both providers happen to agree, which is exactly the case the collation bug lived in.

And in all cases it only ever compares SQLite against whatever server the env var names — never production.

**Text ordering and matching must not depend on collation.** `ORDER BY` and `LIKE` on a text column take the database's collation, which the repo does not control — and **the two databases this app runs on do not agree**:

| | collation | `order by` over `apple, Zebra, banana, Apple, zebra` |
|---|---|---|
| SQLite (local, CI) | BINARY | `Apple, Zebra, apple, banana, zebra` |
| Local test Postgres 17.6 | `C` | `Apple, Zebra, apple, banana, zebra` |
| **Railway production** | **`en_US.utf8`** | **`apple, Apple, banana, zebra, Zebra`** |

Both measured 2026-09-20 (production by the maintainer, `select datcollate from pg_database where datname = current_database()`). **This divergence was live**: the Applications list's "Sort by company" really was ordering differently in production than locally, for as long as the feature has existed, and nothing could have caught it here — the local Postgres agrees with SQLite by accident of how the EDB installer initialised it. `JobApplicationsController.FilteredQuery` and `CoverLetterController` therefore lower both sides — `a.CompanyName.ToLower().Contains(term)` for search, `OrderBy(a => a.CompanyName.ToLower()).ThenBy(a => a.Id)` for the company sort and the cover-letter picker's tie-break. `lower()` translates server-side on both providers and takes the collation out of the answer entirely; it also fixes the UX (a bare sort puts every all-caps name first, and search used to be case-sensitive). Do the same for any new user-facing text sort or search rather than relying on a bare `Contains`/`OrderBy`, whose semantics are EF's translation choice and have changed between versions.

**This is why the fix is `lower()` and not a parity assertion.** A test asserting "SQLite and Postgres agree" would have passed here and proved nothing, because the server it can reach is `C`. Removing the dependency was the only thing that could fix a divergence the test environment cannot see.

**A guard must not hide a defect. This has now bitten three times.** A `catch` written for one runtime condition will happily swallow a programming error that has nothing to do with it, and the symptom is always the same: the feature silently does nothing, or reports a failure that misdirects.

- The autosave helper wrapped `localStorage` in try/catch to survive a private window. A `const` in its temporal dead zone threw a `ReferenceError`, the catch returned "no draft", and answer drafts silently never restored. Server-side tests all passed — they could not see it.
- `application-form.js` wraps ~39 statements in one try and answers every one with "Request failed. Check your connection", so a `TypeError` while rendering a perfectly good response sends the user to look at their wifi.
- Earlier: `DocxText` on a non-Word zip returns `""` rather than throwing, which made a broken file look like an empty one.

**The rule.** `rethrowIfBug(err)` (`wwwroot/js/site.js`) is the first statement of every catch whose try block is more than a line or two; it re-throws `ReferenceError`, which is *always* a bug — an undefined identifier or a TDZ access is never a condition anyone writes a catch for. It deliberately does **not** re-throw `TypeError` (how `fetch` reports a dead network) or `SyntaxError` (how `JSON.parse` reports a bad body), because both are expected here. A caller that knows neither applies re-throws them too — `practice.js`'s `storageBug` does exactly that, since a blocked or full store throws a `DOMException`, so anything else is a bug. **When adding a catch, name the condition it is for and re-throw everything else.**

**Design.** `wwwroot/css/site.css` is the only design system: tokens on `:root`, dark overrides on `html[data-theme="dark"]` (theme stored in `localStorage.theme`). The one exception is `Services/EmailTemplates.cs`: mail clients support neither CSS custom properties nor external stylesheets, so email HTML inlines the literal token values — keep them in step with `site.css`. Sticky/fixed gotchas: the sticky element is `body > header` (a sticky `.site-nav` can't leave its same-height parent); its measured height is `--site-nav-h` (set by `site.js`), used by the Applications table header and `scroll-padding-top`. **`--muted-2` is not a text colour.** At 1.9:1 light / 3.24:1 dark it cannot carry readable text, and no intermediate value fixes that: to reach 4.5:1 it would have to become #67676C / #98989D, which *is* `--text-2` — the tier would collapse rather than darken. So it is reserved for things that are not prose: status dots, the funnel bar, breadcrumb and chevron separators, the search icon, disabled `.page-link`, the `::placeholder` rules (transient hint text, every field has a real `<label>`) and Bootstrap's `--bs-tertiary-color` bridge. The 18 rules that used it for readable text — landing fine print and footer, `.auth-footnote`, `.quick-action-hint`, `.resume-ai-powered`, `.analyzer-model-tag`, the "+N more" counts, the dark `.badge-saved`/`.mini-stat-saved`, `.tour-count` — read from `--text-2` instead. Putting prose back on `--muted-2` re-breaks AA.

**`--accent-soft` vs `--accent-surface`.** `-soft` is a translucent wash for chips and badges sitting on `--card`. It does not work for a full-width box on `--bg`: any wash of a dark blue over a mid-grey only darkens it, so `--accent-text` landed at 4.17:1 there and no alpha fixed it (.05 still gave 4.48). `--accent-surface` is a solid tint *lighter* than `--bg` for that case (`.cl-info-banner`, `.lp-final-box`), clearing 4.94:1 for link text and 4.99:1 for body. In dark the wash already lifts off the background, so `--accent-surface` is just `--accent-soft` there.

The accent and secondary-text values are contrast-load-bearing, not taste: `--text-2`/`--muted` at #6E6E73 measured 4.38:1 on `--bg` (AA wants 4.5), and `--accent` at #0A84FF carried the white `.btn-primary` label at 3.65:1 in both themes. #67676C and #0066CC clear it (4.86 and 5.57); `--accent-h`, `--accent-soft`, `--accent-rgb` and `--focus-ring` moved with the accent so the palette stays one colour. Darkening either further, or lightening `--accent` back for a brighter dark theme, re-breaks AA — white on the fill is the binding constraint. `wwwroot/js/dashboard.js` reads `--accent`/`--muted` at runtime so charts follow automatically; **`Services/EmailTemplates.cs` does not** — its `Accent`/`Muted` literals are still #0A84FF / #6E6E73 and are the one copy left to bring in step.

Non-colour tokens: `--radius` 16px, `--radius-md` 12px, `--radius-sm` 10px, `--radius-pill` 999px, `--shadow-xs/-sm/-/-lg` and `--focus-ring` (both themes), `--ease`, `--duration` 180ms, `--font`.

## 12. Known gaps and deliberate decisions

**Post-audit state (2026-09-20).** Three rounds of the `dd-web-full-test` audit have run and all **20** defects
it raised are closed. The last run was clean in both suites: **914 xUnit tests** and **255 e2e checks across
seven dimensions, 0 failed and 0 skipped** — including Firefox and WebKit, which the first two rounds could
only record as `SKIP`. The write-up with the per-round before/after is `TEST-REPORT.html`, which is gitignored
along with `e2e/artifacts/`: regenerate it rather than expecting it in a fresh clone. Nothing in the two lists
below came out of the audit.

Deliberate — do not "fix":
- `RequireConfirmedAccount = false`: registration signs you straight in and no confirmation email is sent. Password reset is the only email the app sends.
- The public profile (`/p/{slug}`, commit c155efe, migration `RemovePublicProfile`) and uploaded cover letters on the profile (bbb5f48, `RemoveUploadedCoverLetters`) were removed on purpose; profile Age too (`RemoveAgeFromProfile`). Don't reintroduce them. AI-generated cover letters are a separate, current feature.
- Skill gap role matching (`SkillGapService.MatchesRole`) is deterministic and literal-word based: a strict majority of the tag's non-filler words must appear in the role title after a fixed suffix table (`Stem`) and compound joining. No synonyms, role families, fuzzy distance or AI. Commit daf2533 relaxed it once, from "every word" to this strict-majority rule; that is the agreed rule. Do not loosen it further or add synonyms to make demo data split nicely — change the seed (`DemoSeeder.TargetRoles`) instead. Only Applied-or-later applications count; `"[]"` counts as analyzed; card hidden under 3 analyzed.
- Google OAuth consent screen stays in Testing mode (100 test users); only the `gmail.readonly` scope is ever requested; email bodies are never stored.
- Login lockout: `/Identity/Account/Login` passes `lockoutOnFailure: true` and Program.cs sets `MaxFailedAccessAttempts` 5 / `DefaultLockoutTimeSpan` 15 minutes, so five wrong passwords buy a 15-minute wait — a credential guard and a CPU guard both, since each attempt costs a 100k-iteration PBKDF2 hash. The `IsLockedOut` branch is live now: it re-renders the form with `LoginModel.LockedOutMessage`, which is built from the configured window so the stated wait can't drift from the enforced one, and points at password reset as the way out that doesn't involve waiting (`ForgotPassword` stays reachable while locked). **The shared demo account is the one exemption** — its password is handed out by the landing page, so any visitor could otherwise lock it for everyone; `Login.cshtml.cs` matches it through `ConfiguredAccounts.IsConfigured(..., DemoEmailKey)`, never a `==`, and passes `lockoutOnFailure: false` for it alone. Pinned by `Integration/LoginLockoutTests.cs` in both directions: four failures must not lock, five must, and the demo must survive twice the threshold. Accepted trade-off: the lockout message confirms an account exists to anyone willing to spend five failed attempts on one address — standard Identity behaviour, and unlike `ForgotPassword` (which must stay an identical-response endpoint) the cost of probing here is the point.
- Demo account: Gmail Connect refused, tighter AI limit, resume parse served from the canned `ProfileExtractorService.DemoParse()` with no model call and no permit, **a nursing resume on purpose** — the review screen is where a visitor sees the app is not IT-only, and a software parse would read as the default rather than a demonstration; two of its skills are low-confidence so the unchecked-by-default behaviour is visible on screen (`ResumeReviewTests` pins both). Applying that review writes clinical skills, roles and a Healthcare field onto a profile whose 15 seeded applications are all software, so **`DemoProfileReset` (§6) puts the profile fields back per session** rather than leaving it to the nightly reseed: the browser that applied keeps its result, a new `DemoLogin` and any other browser's next `/Profile` view get the seeded profile back. The nightly `DemoSeeder` is still the backstop and still replaces both lists wholesale, which `DemoResetTests` pins. Draft follow-up returns the canned `FollowUpService.DemoDraft` and refuses improve, and Rewrite a bullet returns the fixed `ResumeRewriteService.DemoVariants` (labelled as samples of `DemoSampleBullet`), all without taking a demo AI permit (`[NoAiCallForDemo]`). On Identity/Account/Manage, `DemoAccountGuardFilter` (registered in Program.cs on the whole folder) refuses every POST to credential pages (change password, set password, change email, delete account, all 2FA pages, external logins) with a redirect to Manage and a "Not available on the demo account." toast; ChangePassword and DeletePersonalData render read-only with the notice, the library pages redirect. Manage/Index renders read-only (display name form disabled, POST refused); `ProfileController.SaveInfo` refuses a demo display-name change (JSON `field: "displayName"`) and keeps the stored name when the disabled input is omitted. PersonalData stays open. `DemoAccountGuardTests.Every_manage_page_is_either_guarded_or_explicitly_allowed` fails if an Identity UI upgrade adds an unclassified page.
- Keyword coverage extraction is **deterministic, not a model call** — decided on evidence, not convenience. A prototype was run against the five real postings in the local `app.db` (Shopify 4446 chars, Microsoft 4194, MDA Space 1688, CIBC 1556, IBM 1462) and matched against a real resume PDF: it extracted 19–33 usable terms each (VHDL/FPGA/RTOS/CCSDS/I2C/JTAG for the embedded role, Terraform/GCP/Prometheus/Grafana for the DevOps one, ASP.NET/Node.js/Entity Framework Core/Spring Boot for the two SWE ones) with 1–2 junk chips per capped list of 15. A model call would buy marginally cleaner phrasing at the cost of a cache that must be invalidated whenever the active resume changes, a `[NoAiCallForDemo]` branch, rate-limit interaction and prompt-injection surface on untrusted posting text. Being free is what lets it run on every drawer open and stay uncached, which is what makes "always reflects the resume that is active right now" true by construction. Two failure modes are pinned by tests because they are the real ones: a posting written **without bullet glyphs** (a line opening with a cue word is a requirement, never a heading — getting this wrong silently swallowed every term on those lines), and a posting **flattened to one line** by the bookmarklet's HTML strip (still yields its technologies; only the requirements boost is lost, so ordering falls back to frequency).
- Keyword matching is **literal, on word boundaries**: a posting asking for "SQL" is not covered by a resume that only says "PostgreSQL". Substring matching would make "Java" match "JavaScript", and a false "you're covered" is worse than a false "you're missing this" because the user acts on it by not fixing anything. Real equivalences go through `SkillAliases` instead, which is auditable. One deliberate asymmetry: a term starting with a non-alphanumeric relaxes its *leading* boundary, so ".NET" is covered by "ASP.NET Core" — without it no .NET resume would ever cover it. Where the strict rule bites, `NearMiss` says so on the chip ("your resume has PostgreSQL…") rather than letting it look like a bug. Do not loosen this to substring matching.
- **Phase 6's DB-backed per-day caps were dropped, not deferred** (2026-09-21). The spec asked for per-user per-UTC-day limits enforced in the database, on the grounds that an in-memory limiter does not survive a restart. `AiUsageLimiter` already existed and the spec did not know it: adding the DB caps would have put two limiters over one OpenAI budget, which is worse than one that resets on deploy. The audit behind that call — coverage, the restart and per-instance limits, and why per-IP is already moot — is in §8.
- **A separate practice history view was considered and deliberately deferred (2026-09-21), with triggers.** Everything it would need is already stored — score, feedback, timestamp, prior attempts — so the question was never feasibility, it was whether there is enough data for it to say anything. At ~15 questions there is not, and three of the four things it would show already exist: date order is the list's default, the score trend and weakest topic are the progress card, and retries are on each card. **Do not rebuild this reasoning from scratch — check the triggers instead:**

  1. **40+ answered questions.** `PracticeProgress.MinAnswersForTrend` is 20 precisely because a trend needs two full windows behind it; a sparkline through six points invites reading a slope that is not there.
  2. **3+ topics with at least 3 answers each.** `MinAnswersForWeakestTopic` is 3, and the generator is tuned for narrow topics ("connection pooling", not "databases"), so a small set spreads one answer per topic. A weakest-topics table below that floor is noise presented as insight.
  3. **Retries becoming common.** `PriorAttemptsJson` is null for nearly every row today.

  **The third is the real signal; the first two are just usage.** Someone retrying often has a question the cards genuinely cannot answer — what changed between a 2 and a 4 — and that is when a history view stops being a report and becomes a tool. The narrow version of it shipped instead: `_PracticeQuestion.cshtml` shows attempts **side by side** rather than stacked, which was the one gap, confined to a view, and commits nothing.
- Interview prep questions are **appended, not replaced**, since the Phase 3 merge. The old behaviour (one session per application, overwritten on regenerate) went with `InterviewPrepSession`; its table was dropped rather than migrated because the rows were regenerable AI output and converting the JSON blobs would have meant parsing JSON inside a migration.
- No status history: analytics use current status (Interview/Offer = response).
- Antiforgery failures and other 400s surface as 404 because status-code pages re-execute through `/Home/NotFound`.

**Deferred to after the Phase 1-5 deploy — one cluster, and several of them unblock each other.**
Recorded together because picking any one up in isolation wastes the others' groundwork:

1. **Seed bank (spec §5.2) — deferred with reasons, not forgotten.** The spec asks for ~40 pre-generated questions per (`FieldCategory` × `PracticeDifficulty` × `QuestionCategory`): 13 × 3 × 3 = 117 combinations, **~4,680 questions and ~936 API calls**. Three things to weigh before starting. (a) Both stated rationales are weaker than when the spec was written: the demo already has a tighter `DemoPermitLimit`, and generation is one call returning five questions in a few seconds, so "instant first load" buys little. (b) **The storage design fights the schema** — it calls for global rows at `UserId = null`, but `UserId` is non-nullable and the unique index is `(UserId, PromptHash)`, so it needs a migration on a shipped table. If it is ever built, a runtime JSON file under `Data/Seeds/` (the `target-roles.json` pattern, already used by `TargetRoleSeeds`) gets the same result with no migration and no nullable key. (c) Quality is unverifiable at that scale outside software — nobody here can judge whether a Hard nursing question is a good one.
2. **Fold `InterviewPrepService` into `PracticeQuestionService`.** One generator, not two against one store. **The known cost of leaving it:** prep questions land with `Difficulty = Medium` and `Topic = ""`, so **`TopicKey` cannot dedupe them against practice questions** — the mechanism that was measured to do nearly all the deduplication is blind to everything the prep page generates. A known gap with a known fix, not a bug to rediscover. Blocked by (3).
3. **`Views/InterviewPrep/Prep.cshtml`'s inline script → `wwwroot/js`.** Blocks (2), because consolidating changes the `{category, question, tip}` JSON that script reads. Also the last inline block outside `_Layout`, so closing it is what lets the CSP go from report-only to enforced (§8).
4. **`OpenAI:BaseUrl` in the five services that ignore it**, `InterviewPrepService` among them — which is what would make (2) verifiable against a stub instead of the real API. See the entry below for why this one is more than tidiness.
